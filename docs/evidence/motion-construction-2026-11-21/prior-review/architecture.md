## Findings

1. **P2 · Film and browser review lose distinct reader pictures.** [The checker](../../tools/lib/explain-check.ts#L706) distinguishes incoming responses at one durable state. [Film](../../tools/lib/explain-film.ts#L52) visits one shortest path per durable state. [Served review](../../tools/lib/explain-live-review.ts#L42) omits paths back to the starting state, then chooses just the first event if all paths return there. The public fixture has one durable state and two accepted events, `mark` and `ship`. Native pixels are green initially, red after `mark`, and blue after `ship`. Replaying `mark,ship` produces eight samples from red to blue. Film creates just `[mark]` and `[ship]`, both from green. The actual served-review planner selects only `[mark]`, even though a reader can see blue on their first press. The individual traversal routines are inherited from PR 112 and main. Adding presentation-aware exploration exclusively to `check` leaves the integrated workflow inconsistent. This affects the advertised bounded coverage of `film` and the published rationale for visiting first-press pictures. [Fixture and sampled colors](architecture/contexts-proof.json) · [Reproduction](architecture/contexts-proof.mjs) · [Film contract](../../docs/REFERENCE.md#L844)

   Keep one repository-internal enumeration of distinct reachable picture origins within the declared model bound. It should retain a representative legal event history, model state and incoming result, along with accepted/refused/beyond edges and graph completeness. The checker can consume every admitted edge, film can render each distinct origin and press, and served review can keep a smaller sample with mandatory coverage of distinct immediate responses. Reuse the existing reader replay for rendering. Browser cost can stay bounded for deeper histories. Put the two-event fixture through all three entry points.

2. **P2 · Source-checkout review receipts survive changes to their verifier.** The [review fingerprint](../../tools/lib/explain-review-plan.ts#L185) lists `explain-check.ts` and the story reviewer by hand. It misses the new `tools/lib/explain-motion-rules.ts` called by the checker, and inherited `tools/lib/explain-film.ts` used for mid-play captures. Both are absent from the current 150-file page-build manifest as well. In a disposable review tree, replacing either helper with a top-level throw produced an identical reviewer fingerprint. Replacing a named verifier changed the fingerprint. The [merge gate](../../tools/lib/explain-review-plan.ts#L337) therefore cannot reject an otherwise valid older receipt solely because one of these verifiers changed. Current CI executes the current checkout and the packed path hashes bundled tools. The defect affects source-side evidence identity and future reuse or concurrent-edit detection. Compute a transitive graph of review-time imports from review/check entry points, reusing the page producer's import walker. A narrow test should change a transitive verifier and hold page identity constant while review identity changes. [Fingerprint control](architecture/receipt-proof.json) · [Reproduction](architecture/receipt-proof.mjs)

3. **P2 · A failed film rerun damages retained evidence and can delete user files.** [Film startup](../../tools/lib/explain-film.ts#L40) recursively removes the caller's entire `<out>/frames` tree. The [manifest and HTML](../../tools/lib/explain-film.ts#L66) are written at the end. A real CLI run produced three sequences and ten frames. A second run against that output exited 1 when a reader transition threw. The old success manifest and HTML remained, two of its PNGs disappeared, and a separate `frames/notes.txt` created by the fixture was gone. This is inherited unchanged from PR 112. Render into a uniquely owned generation, publish the manifest after it succeeds and retire only files from the previous successful manifest. Serialize publication if two invocations target the same destination. [CLI results](architecture/film-output-proof.json) · [Reproduction](architecture/film-output-proof.mjs)

## Integration and simplification choices

For a claim that the visual workflow covers the repaired class, fix the picture-origin mismatch and bind the new verifier to source review receipts. Track film output ownership against its originating parent PR. A historical Poppy score alone cannot decide any of these.

Preserve both parents. Main has already been merged. Rebasing directly onto main would bring PR 112's unreleased reader changes and frozen benchmark into the base-relative review. Resolve the PR 112/main integration first using the existing, tested conflict resolutions, then review motion against that integrated parent. This makes ancestry legible at the cost of checking that new parent tree and the resulting motion delta. Add driver, scene, and evidence changes as separate review units if new corrective work is necessary. Keep per-chapter semantic assertions near their scenes and shared rendering/reachability rules in their respective tool owners.

The benchmark and frozen visual receipts provide inspectable historical evidence. A compact manifest with stable artifact links could remove the largest media from future diffs if a durable archive and retention policy are available. This is an optional maintenance trade-off. Existing commits and immutable links enable readers to inspect the retained history today. The memory experiment also needs its untracked source SVGs in `out/motion-all59-audit`; its [README](../../docs/evidence/motion-raster-resource-2026-11-21/README.md#L18) discloses that dependency. New evidence packs should either include the exact inputs or provide a single revision-pinned command to reconstruct them.
