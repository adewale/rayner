# Engine docs: a map

The engine is `src/`, exported through `src/index.ts`. It has no runtime dependencies and never shells out: token colours, Git hunks, diagram snapshots and requested lettering are captured at build time and checked in. Start with [engine fundamentals](ENGINE-FUNDAMENTALS.md), then run the [extension recipes](EXTENDING.md). The explainer layer on top (stage, diagrams, checks, page) is in [the reference](REFERENCE.md), which also [names the explainers](REFERENCE.md#engine-features) that use each feature. [Upstream](UPSTREAM.md) records what changed from Lantern.

## Correctness by construction

Correctness comes from construction first: types, private state, module-private functions and one entry per job make the wrong use impossible to write, or the right use the only and easiest path. A runtime check stays only at an untyped boundary (`script.md`, a URL, a JSON snapshot, a command's arguments, a file read from disk), for a value a type cannot express (a finite positive size, a hex colour, a unique key, the length of a list computed at run time: `play()` and `new Machine()` refuse an empty one, since a scene maps its animations from its data and may read its events from it, and an array's type does not carry its length), and on the one typed path the types do not check: `Object.assign(m, { center })` type-checks whatever `center` holds, and `m.center = () => …` assigns a function, so assigning any of the eight method names a scene most often takes for a part (`box`, `center`, `width`, `height`, `left`, `right`, `top`, `bottom`) throws a `TypeError`. A misuse that TypeScript prevents, or that takes plain JavaScript or a cast to write, is not checked at run time. So `Animation` has no public lifecycle method: a play, a group and a `Succession` begin, draw and finish an animation through the engine's module functions, which call only its protected hooks, and read its timing and phase from private fields. The engine keeps every other member it reads or calls on `Scene` and on each mobject, animation and sink class an entry point exports in an ES private field, under a symbol or in a module function, so no member an author writes on a subclass of one, under any name, replaces or shares a name with one: `test/scene-lifecycle.test.ts` builds each of those classes, found from the entry points' exports, shadows every name the engine's members have and finds each run unchanged. `Diagram` and `Machine` are made, not extended, and hold no such promise. A mobject's children, parent and key are private fields that only its own methods and `keyed` change. One rule a type cannot carry stays a rule: `copy()` cannot run a subclass's constructor, so a mobject keeps its state in ordinary fields or under symbols, never in ES private ones, which the copy would lack; a type cannot tell a `#` member from a TypeScript `private` one or a protected override, so `copy()` refuses a class that declares one, naming the class and the member, where the copy would otherwise fail at its first use (`test/core.test.ts` copies every exported mobject class and finds the copy drawn as the original, and the original unchanged by a change to the copy).

Five invariants hold the engine together. The API enforces each one where it can, and a check covers it where it cannot.

1. **A frame is a pure function of time.** The clock is the frame count. An animation fixes its endpoints when it begins and computes each frame from alpha alone, so a seek can skip interpolations and must render the byte-identical frame a full run renders. An active updater may depend on earlier frames, so a play with one replays frame by frame ([fundamentals](ENGINE-FUNDAMENTALS.md#updaters-derived-pictures-and-seeking)). `rayner check` fails a step whose direct link draws differently from playing to it: it seeks to each step's middle, its second-last frame and its resting frame, the one a link shows, and it compares the picture as each step ends, after its last play has finished, with that resting frame.
2. **Each mobject has one writer.** Every animation reports the mobjects it writes (`targets()`), and `play()` rejects two animations that drive the same mobject, or an ancestor and its descendant, at once, and one animation listed twice. What begins later in the play is checked as it begins, against everything else the play drives then: a `Succession`'s member at its turn, and what an action's beat or a machine's transition makes when its turn comes. [A follow](CHOREOGRAPHY.md#following-one-number) writes only the targets it names. Updaters are exempt: they run after the animations each frame, so what an updater writes wins ([fundamentals](ENGINE-FUNDAMENTALS.md#updaters-derived-pictures-and-seeking)).
3. **Identity is a key.** A part is keyed with `keyed(m, key)`, the one way to set the read-only `key`, and addressed by it (`find`, `findAll`) and kept across morphs by it ([`matchByKey`](MATCHING.md#keyed-components)); `become` refuses to drop a keyed child, and `rayner check` fails two parts with one key at the end of a step, whatever the key. What a part is for, which many parts can share (the stage's `'backdrop'`, `'heading'` and `'chrome'`, a diagram's `'frame'`), is its `role`, never its key. A mobject's number, the renderer's, is private to the engine.
4. **Anything a reader can reach is a view of state.** A [`view(scene, draw)`](VIEWS.md) keeps its `draw`, `s.steps` records each step's, and a [`Machine`](MACHINES.md) is made of views. So `rayner check` redraws every staged step and every reachable machine state from the state alone and compares, and a fidelity test can compare any view with the traced state at every step.
5. **Every claim can fail.** An [invariant](EXTENDING.md#hold-an-invariant-on-every-frame) that never holds in a run fails, and `test/explain-gates.test.ts` gives each check one seeded defect it must reject. A claim of success names the check that proves it and the deliberate defect that check was shown to reject.

Three records say what happened, each answering a different question. The **trace** (`traceScene`) is what each step showed: its timing, the model before and after, what was shown (`shown`) and the step's evidence. **Evidence** is what an animation decided, recorded as it began ([fundamentals](ENGINE-FUNDAMENTALS.md#steps-state-and-evidence)). The **receipt** is what a build produced, from which inputs: the scene's source and snapshot hashes, the page's `artifactHash`, each scenario's steps and the page's size ([the reference lists its fields](REFERENCE.md#headers)).

## Layers

The code is a stack, and each layer imports only the layers under it. From the bottom:

| Layer | Modules | May import |
| --- | --- | --- |
| Engine | `src/` | Nothing else in the repository but the vendored shaper, `vendor/glyph.js` |
| Explain core | `explain/`: `view.ts`, `state.ts`, `machine.ts`, `live.ts`, `choreograph.ts` (views, machines, the run to a live step, and state); `action.ts` (what a stage or diagram action returns); `look.ts`, `palettes.ts`, `layout-direction.ts` (the look); `words.ts`, `trace.ts`, `script.ts`, `claims.ts`, `caption-looks.ts` (words); `diagram-snapshot.ts`, `diagram-text.ts` (diagram snapshots: their types, keys, validation and findings, and a captured label's text); `settings.ts`, `page-query.ts`, `intent.ts`, `mermaid.ts`, `audio.ts` | The engine |
| Diagrams and panels | `explain/diagrams.ts`, `explain/labels.ts`, `explain/panels.ts` | The core and the engine |
| Drawing kit | `explain/drawing.ts`, `explain/annotate.ts`, `explain/geo.ts`, `explain/seen-from.ts` | Diagrams and panels, the core and the engine |
| Stage | `explain/stage.ts`, and `explain/index.ts`, the `rayner/explain` entry point | Every layer above |
| Author tooling | `explain/describe.ts`, `explain/project.ts`, `explain/test-helpers.ts`, `explain/testing.ts` (with the engine's half, `src/testing.ts`) | The library |
| Internal interface | `src/internal.ts`, `explain/internal.ts`: what the player, the command and diagram capture use beyond the entry points | The library |
| Player | `app/` | The library |
| Command and tools | `tools/` (the command, `rayner-cli`), `integrations/agentic-mermaid/` (diagram capture, which the command runs), `tools/repo/` (repository only) | Anything; the command imports nothing repository-only |

An entry point re-exports from its own layer and the layers under it. The library (the first seven layers) imports no package and no Node module, which is how `rayner` has no dependencies and runs in a page; `loadProject` and `loadSnapshots` in `rayner/testing` read files through `process.getBuiltinModule` when they are called, so they alone need Node. The player imports only the library. A diagram snapshot is Rayner's own format, so it lives in the explain core; only capture, which writes snapshots, talks to Agentic Mermaid, and it sits with the command. `test/layers.test.ts` holds these rules for the engine, every module under `explain/` (the test reads the table above, so a new module must be placed in one of its rows, and a row may name only modules that exist), the player, and the command, which imports the library, the player, diagram capture, the vendored shapers, its own modules and packages, but nothing repository-only (`tools/repo/`, `tools/oracle/`, the tests, scenes, recipes or benchmarks). `test/package-boundary.test.ts` holds the command to its bundle and the library to its entry points, and `test/scene-imports.test.ts` holds scenes to the entry points.

A constant more than one layer needs has one source, a leaf module: the frame, its home box and the SVG units per scene unit in `src/units.ts`, and the query keys a page reads itself in `explain/page-query.ts`, which the player, the host loader, the resize protocol and the share pages read. `loadProject` and the command collect a project by the same steps in `explain/project.ts`: `adoptExplainer` refuses an unknown meta key, adopts the script's intent and gives the scene its default id (`sceneIdOf`), and `traceScenarios` traces every scenario against the snapshots and holds its steps to the step rules; the command adds capture, lettering cuts, the stage's colours and live steps around them.

Where the code departs from the stack:

- **The kit names the stage's type.** Each kit function takes the stage `s` first, to read its colours and text shaping, so `drawing.ts` imports the `Stage` type. Its values come only from the core and the engine; the test allows that one type import and no other.
- **The engine carries a step's caption, what is shown, and the trace's JSON hooks.** `src/scene.ts` keeps them because the engine's own work reads them:
  - The caption-reading hold (`StepMeta.caption`, `Scene.captionWpm`, `Step.hold`) is part of the timeline. It adds frames to every captioned step of every scene, with a stage or without one (the command and the player run both), and seeking, the trace and the player stop at it. Moving its arithmetic into `explain/` would need each scene to register it, through a stage every scene must make before its first step or a base class every scene must extend, and a scene that missed it would play a different timeline from the same source.
  - `scene.shown` is half of the typed scene, `Scene<Model, Shown>`, which views, machines and staged steps take their types from, and the trace records it at the end of every step beside the state. Moving it means a base class from the explain layer for every scene.
  - `stateJson()`, `shownJson()` and `addJson()` are how the trace reads a step's state and what is shown. A helper adds its own JSON with `addJson`, as the stage adds its picture's description and recorded walks are kept; the hooks name nothing of an explanation.

  A step's title, line and kind (`StepKind`) belong to the explainer layer, and the engine reads none of them: `explain/script.ts` declares them on the engine's open `StepMeta` interface, so they are typed wherever `rayner/explain` is loaded. `test/layers.test.ts` holds the engine to that.
- **The explainer layer uses the engine's `@internal` interface.** The explainer layer imports the engine's modules directly, and beyond the public API it uses a short list of `@internal` names the published types leave out. The engine owns every animation's lifecycle (its begin, frames, finish and clean-up); where the explainer layer needs a piece of it, it extends or calls an engine name for that concept:

  | Engine concept | Names | Used by |
  | --- | --- | --- |
  | An animation of beats: decided once what it reads is ready, plays once, alone (a play per beat) or composed (its beats made at their turn), and passes a play's easing to them | `Beats`, `BeatPlan`, `Beat` (`src/animation.ts`) | an action (`explain/action.ts`), and the stage's and a diagram's plans |
  | An animation made at its turn, from the pictures on screen then | `MadeAtTurn` | a machine's transition |
  | An animation that runs another inside it, made as it begins | `Enclosing` | a view's sync and tween, a choreographed entrance |
  | An animation run to its end at once, outside a play | `finishAtOnce` | a diagram's hidden parts |
  | The scene a state change belongs to | `playsOn` | a machine's state change |
  | A same-structure morph, a sketch's family rows | `knownTransform`, `families` | a view's index match, a sketch |
  | A run stopped as a step ends, which draws its picture to any sink | `stopAt` (`src/scene.ts`) | the run to a live step (`explain/live.ts`) |
  | What the scene draws last, or leaves out of a picture | `keepOnTop`, `setDrawn` | the stage's heading |

  The rest are mobject and text internals that diagram labels and annotations read (`affine`, `textRun`, `advanceBox`, `buildText`, `interpolateData`, `matchingFrameFor`, `mergeLeaves`, `curveCount`, `replaceChild`). The engine's lifecycle functions and hook symbols (`beginAnimation`, `whenReady`, `settle`, `cleanUp` and the rest) are not among them: only the engine calls them. Above the library, the command explores a machine through its `reachable`, `after` and `transitionPlay`, the player asks a machine's `outcome`, and the command matches the renderer's records to their mobjects by `mobjectId` (`src/internal.ts`). A member is reached through its object, so no module can list it: `test/layers.test.ts` lists every `@internal` member used across the layers, and every engine module-level `@internal` name the explainer layer uses, with the files that use it and why, read by the type checker from the comment on the declaration or on the statement that holds it, so a new use fails until it is listed. Each engine member authors' subclasses could shadow is ES private or keyed by a symbol, and each module-level hook is a function that reads a private field, so none of these is reachable from a scene through the entry points.

### The internal interface and the command's contract

The player (`app/`), the command (`tools/`) and diagram capture (`integrations/`) import the library as an outside project does, through its entry points, and beyond them only through two barrels: `src/internal.ts` for the engine and `explain/internal.ts` for the explainer layer. Each re-exports, by name, every module-level name those layers use that no entry point exports, so the interface they depend on beyond the public API is one list per layer, counted and reviewed where it changes. `test/layers.test.ts` fails an import that reaches any other library module from above, a barrel name that an entry point already exports, and a barrel name nothing above uses. The barrels are not entry points: the package does not export them.

`rayner-cli` depends on the library in three ways that the package's exports do not show, and the release keeps all three:

- **The private specifier.** The command's bundle reaches the library's compiled modules, the barrels and entry points among them, by `#rayner/…` (`#rayner/src/internal.js`), which a resolve hook it registers at startup (`tools/installed.ts`) maps to the installed `rayner` package's `dist/`, for the command's own modules only, so the command and the scenes it loads share one engine. It imports the vendored shaper the same way (`#rayner/vendor/glyph.js`), and bundles no copy of either (`test/package-boundary.test.ts`).
- **Compiled sources.** The page build bundles the player with the library's TypeScript sources, `src/` and `explain/`, from the installed package, and reads the shaper from `dist/vendor/glyph.js`; so `rayner` ships its `.ts` sources as a build input of `rayner-cli`. The page build's own font inputs (`vendor/font-data-sfnt.json`, `vendor/glyph.pin.json`) ship with `rayner-cli`.
- **Exact version.** `rayner-cli` depends on `rayner` at exactly its own version and refuses any other at startup (`tools/lib/roots.ts`), since the barrels, the `@internal` members and the sources are not kept stable between versions. `npm run pack:smoke` installs both archives and runs the command against the library.

## What belongs in Rayner

Sort a feature request with one question: does it check, ground or publish the result, or does it do work a capable author would do anyway?

- **Belongs:** work an author, human or model, cannot easily do or verify by eye, and that should be the same on every page: testing a model against its source, measuring what is painted, reviewing the served page, deterministic frames, portable and accessible pages, a description and transcript for every picture, and making the reader's own actions checkable ([the live machine](https://github.com/adewale/rayner/issues/88)). This work gets more valuable as authoring models improve, because there is more output to check.
- **Does not belong:** work that needs judgement and improves with the author's skill: wording, pacing, narration, layout and how to teach. Rayner gives the author what that work needs (`describe`, `see`, the resting-picture descriptions, step timing) and leaves the work to the author, because a feature here would cap good authors at the feature's level. The same goes for guidance: the [authoring skill](../skills/rayner-explainers/SKILL.md) says what must be true and how it is checked, not how to draw.

When a request is the second kind, the answer is usually to expose the data the author needs rather than build the behaviour.

**Design records.** A design document ends with what was tried and not kept, and why, as Lantern's performance notes did and as [sampled parameters](PARAMETERS.md), [machines](MACHINES.md) and the [vocabulary](VOCABULARY.md) do. A proposal that cannot name its rejected alternatives, or the existing explainers it changes, is not ready.

## Primitives considered and not built

A review on 2026-11-03 found that 34 of the 40 explainers then in the collection (a dated survey figure, not a current count) cleared the stage and redrew each step, and that the duplication the collection carried was layout arithmetic, not identity. It added keyed components (`matchByKey`, [matching](MATCHING.md#keyed-components)) and a `table()` in the drawing kit that places its measured columns and keys its header, rows and cells (`key:row:column`; a duplicated row key is refused), which python-dict's machines morph by. It turned these down:

- **Keyed collections with separate slots.** Which entity an item is, which slot it occupies and where it is shown are model facts, and every scene's model already holds them (`ring-buffer` keys values `slot:${i}`). Once keyed components match, a collection is a key-naming convention, and moving entity identity into the drawing layer would take it away from the oracle-tested model.
- **Persistent attachments.** In a redraw scene every label is recomputed anyway; in a morphing scene the `View` rebuild repositions arrows, and `Labeled` and a diagram picture's notes (`d.picture(marks, { notes })`, or one `d.notePicture`) cover static anchors. An attachment system needs a geometry plan, cycle rejection and a missing-target policy, which add up to a reactive constraint graph; "points are the truth" excludes one.
- **A parameter rig.** One explainer, the token bucket, needed several drawings to follow one number, so the exported shape is a view's tween and a transition's follow, both [one sampled number](CHOREOGRAPHY.md#following-one-number). [Sampled parameters](PARAMETERS.md) records the survey.

`s.steps` keeps clear-and-redraw as its default transition: an author opts into entity continuity, with a view or a machine, when successive pictures show the same entities.

## Public names

The package has an entry point per audience. A scene is written with `rayner`, `rayner/explain` and `rayner/drawing`, and opts in to `rayner/geo` (3D and the globe). `rayner/output` draws a scene's frames outside the built page, for a host page or a tool, and `rayner/testing` holds what an author's tests and tools use; no scene may import it ([the reference lists both](REFERENCE.md#testing-and-tooling-api)).

The package has no dependencies; the `rayner` command is the separate `rayner-cli` package, at the same version. The package exports its entry points and nothing else, so an outside project can import no other module. The command shares the library's compiled modules with the scenes it loads without an export, by a private specifier ([the command's contract](#the-internal-interface-and-the-commands-contract)). `npm run pack:smoke` checks that an outside project cannot import `rayner/internal/...` or the private specifier.

A public class member is one an author uses, documented in [the reference](REFERENCE.md); the rest are `private`, `protected` (a hook a subclass overrides, such as `Mobject.copyData`) or marked `@internal`, which `stripInternal` leaves out of the published declarations. The collection is type-checked in the repository against the engine's source, where an `@internal` member is still visible, so `npm run pack:smoke` also type-checks every explainer, its tests and every recipe, engine imports rewritten to the entry points, against the packed declarations: a scene or a scene's test that uses an implementation detail fails there. It builds fewer from the install: the lettering fixtures, `font-metrics` (natural font replay) and `layout-direction` (panel direction). What a build checks beyond the type-check is the installed command's own paths, which the same compiled engine runs for every scene, so a build per explainer would repeat those paths rather than reach new ones.

Every value an entry point exports needs a reason to be public. Rayner computes it where it can, so [`test/public-names.json`](https://github.com/adewale/rayner/blob/main/test/public-names.json) lists only what no import can show:

- **used**: an explainer, a tutorial scene or a recipe imports it and uses it. Who uses it is computed from their imports, through the collection's own re-exports, and never written down.
- **tooling**: it lives in `rayner/output` or `rayner/testing`, and the ledger says who uses it outside a scene and for what (`tooling`: a host page, an author's tests or tools). Every name in those two entry points needs this written reason, even one a recipe uses, and no name elsewhere may have one. Living in a tooling entry point is not by itself a reason to be public: a value only the build, the page or the command needs stays internal, as the lettering functions the build and a lettered page call do.
- **taught**: a guide section teaches it and a test runs it. The ledger names the section's anchor and the test file (`guide` and `test`), and both must exist and mention the name. `Frame` is taught this way (the camera guide and `test/camera.test.ts`); every other scene name is used. A Manim name keeps a test that it means what Manim means whatever its reason: `smooth`, `rushInto`, `rushFrom` and `thereAndBack` are compared with Manim's own functions in `test/manim.test.ts` (latest-search rushes in, token-bucket rushes out and goes there and back; no library code has used `thereAndBack` since `Indicate` went), and `ArcBetweenPoints` turns counterclockwise for a positive angle, as Manim's does (`test/core.test.ts`).

A name may also say what `rayner check` verifies about it (`check`), led by the name of a check in [the reference's table](REFERENCE.md#checks): `view` and `View` say "Views", `Machine` says "Machines", and `having` says "Views", since a draw that narrows with it throws on a state of another shape. `test/public-names.test.ts` fails when a public name is neither used, tooling nor taught, when a tooling name has no written reason or a name outside the tooling entry points has one, when a `taught` section or test is missing or does not mention it, when a `check` names no check, and when the ledger lists a name no entry point exports. It also renders [the reference's engine features table](REFERENCE.md#engine-features) and [the skill's examples](../skills/rayner-explainers/SKILL.md#start-from-an-example) from the same file and fails when either document differs, and it fails an example that claims a name or a member its scenes do not use. `node tools/repo/public-names.ts` prints every name with its reason and users; `--write` renders the tables.

**Every public name documented.** The public surface is every value and type an entry point exports, every public member of an exported class (a type-only class such as `Card` included) and the stage's members. A member that overrides an exported ancestor's is the ancestor's name (`Text.interpolate` is `Mobject.interpolate`), and one that implements an exported interface's is the interface's (`NullSink.frame` is `Sink.frame`). `test/public-names.test.ts` fails when a guide in `docs/` does not name one in a code span or block. A value or a type is named by its name. An options bag, a type whose name ends in `Options`, may instead appear in the signature of a documented function, constructor or member, which shows it wherever the call is written; every other type must be named. A member is named by `.name` or a code span it leads, in a section (the text under one heading, down to the next) that also names its owner class, or as `r.name` with the receiver the [error messages](#error-messages) write for its owner (`s.card`, `d.walk`, `view.sync`, `machine.send`, `m.shift`, `code.span`), so a member documented on another class does not count: `machine.spec.start` does not document `Line.start`, `d.labels` (another class's receiver) does not document `Card.labels`, and `scene.ts` (a file) does not document `Machine.scene`. The gate establishes that a section names a member, not that it explains it: a bare span that happens to be the member's name, `build` for the command beside `Text`, still counts, and telling the two apart would need the guides to mark which is which. A name with no author purpose (the renderer's point buffers, a morph's alignment, `play()`'s machinery, the lettering snapshot's wire formats) is made `@internal`, `protected` or private rather than documented; `interpolateSubmobject`, `doBegin`, `doInterpolate` and `doFinish` are `protected`, the hooks a custom animation overrides, and a mobject with points of its own overrides the public `pointArrays`, `boundingPointArrays` and `pointKind`. `stripInternal` hides a name from the published types but cannot stop an author's subclass from reusing it, so an engine member of `Scene` or of an exported mobject, animation or sink class is never a string-named `@internal` or private member: it is ES private, keyed by a symbol, or a module function. While a decision on such a name waits it can be listed with why in `UNDOCUMENTED` in `tools/repo/lib/public-docs.ts`, which is empty; an entry there that a guide documents, or that is not public, fails. `node tools/repo/public-names.ts --docs` lists the surface, says of each name whether it is documented, and counts it.

**Admitting a new abstraction.** A proposal for a new public name says which reason it will have, and, when it is an abstraction rather than a value, what `rayner check` can verify about it once it exists: a view is redrawn from state at every step, a machine's reachable states are explored, a keyed part is held to one key per part. A name whose correctness no check can see is admitted only when a test runs it and a guide teaches it.

A name only the library uses is internal, and a name nothing uses is cut: the vector helpers and the diff internals are internal, and the engine exports no direction vectors, no Manim colours and no `Indicate` or `Flash` ([the changelog lists the names 0.2.0 removed and what replaces each](../CHANGELOG.md#removed-from-the-public-api)). An explainer colours from its stage's look, and engine defaults take the scene's colours ([fundamentals](ENGINE-FUNDAMENTALS.md#geometry-and-paint)); a mark that fades before the resting picture is not offered ([vocabulary](VOCABULARY.md#names-deliberately-kept)).

## Error messages

An error an author can see says which call failed, what is wrong with it and, when the fix is known, how to fix it: `card(): the row "Hits" has 3 values for 2 columns; give one per column, or one to span them`.

- **Prefix.** The message starts with the API the author called and a colon. A function is written as called, `card():`, `having():`, `mermaid.pie():`; a constructor as `new NumberLine():`; a method with its receiver as the reference writes it: `s.card():` on the stage, `d.walk():` on a diagram, `view.sync():`, `machine.send():`, `t.choreograph():` and `c.follow():` in a transition, `this.play():` and `this.step():` for the scene's own methods, `m.become():` for any mobject, `code.span():`. A declaration is named by its path, `meta.watch:`, `static settings:`, an author's class that a copy cannot carry by `class Bars:`, and a file the scene keeps beside it by its name, `scene.snapshots:`, `scene.lettering.json:`, or its path (`script.md`). A stage verb built on a kit function names the verb: `s.card()` reports its card's errors as `s.card():`, the kit's `card()` as `card():`.
- **Sentence.** After the prefix comes one sentence that continues it: it starts in lower case unless it starts with a name, names the value at fault (a string in quotes, as `JSON.stringify` writes it), and ends without a full stop. Its parts are joined by semicolons.
- **Fix.** When the fix is known it is the sentence's last part, after a semicolon, as an instruction: `; reveal it first`, `; run rayner snapshots`.
- **Class.** `TypeError` for a value of the wrong type or shape, which only an untyped boundary or a path the types do not check meets: not a function or an object, a field missing, a key the declaration does not take, a value assigned over a mobject's method, an author's class whose ES private member a copy cannot carry. `RangeError` for a value of the right type outside what is allowed: a number out of range, a name that is not one of the allowed names (a style, an event, a step), a line past the end. `Error` for the rest: a conflict between values, such as two parts with one key or two animations on one mobject, and a call the scene's state does not allow, such as an action played twice.
- **No internal ids.** A mobject is named by its key, else its text, else its kind, `the Rectangle keyed "slot:3"`, `the Text "len 0"`, `a Circle`, never by the renderer's number, which is private to the engine. A kind takes the article it is read with: `an Arrow`, `a Circle`, and, for a name read letter by letter, `an F`, `an SVGPath`.
- **One exemption: frozen metadata.** A write to a step's frozen metadata (`currentStep.meta`, a trace's `meta`) throws the language's own `TypeError`, which names the property but no call.

The command prints a failure after `rayner:`, so its own usage errors carry no other prefix (`rayner: "chek" is not a command; rayner --help lists the commands`), while an error from a scene's code or declarations keeps the prefix that names it (`rayner: meta.lettering: "Grk" is not an ISO 15924 script code, such as Grek`). `test/error-messages.test.ts` reads every `new Error(`, `new TypeError(` and `new RangeError(` in `src/`, `explain/` and the player (`app/`), and fails a message that does not start with a prefix, that ends with a full stop, or that interpolates a mobject's id. A prefix the code computes is read from a variable named `api` (the call that passed its name down), `call`, `where` or `name` (or their plurals), whichever file computes it. Whether a computed prefix holds the right call, and whether the class and the fix are right, is for review.

## Locale

What Rayner writes is the same on every machine: a lettering snapshot, a trace, a description, a receipt and a page do not follow the machine's locale or the engine's locale data. Strings are ordered by UTF-16 code unit (`byCodeUnit` in the command, so `scene.lettering.json` stores its runs and font inputs in one order everywhere), and JSON values are compared and deduplicated with their keys sorted (`canonicalJson` in `src/json.ts`), never by the order they were written in. A number a reader is shown, a watched value or a count in a French description, is written by `writeNumber` in `explain/words.ts`, from the repository's own decimal mark and group separator for each description language, rather than by `Intl.NumberFormat`, whose separators differ between Node's ICU and a browser's data; so a transcript the command writes and the page agree. No Intl object is used: a tab stop counts columns by character category (`expandTabs` in `src/text.ts`), as font fallback decides what draws with the character before it, rather than by an `Intl.Segmenter`, whose grapheme clusters follow the engine's ICU version. `test/locale.test.ts` reads the code for `localeCompare` and `toLocale…` calls and Intl objects, outside a short list of exceptions whose output is never saved, and checks that lettering run keys sort the same under two locales.

## Out of scope

- **3D in the engine.** The model is 2D point buffers drawn as SVG paths; a z-buffer, lighting and a 3D camera would be a second engine. A 3D picture is a drawing instead: [`seenFrom(model, viewpoint)`](REFERENCE.md#3d-seenfrommodel-viewpoint), from the opt-in `rayner/geo`, turns a model and a viewpoint (plain state, turned by a view's tween) into ordinary keyed 2D pieces in an explicit depth order, which `depthOrder` checks.
- **Boolean path operations** (union, intersection, difference). Robust curve clipping is a geometry library in itself; an approximate one would break exact points, and a dependency would break zero runtime dependencies.
- **Runtime LaTeX.** A TeX engine and its fonts are a large dependency, so neither a page nor a build runs one. Maths is typeset once, when its snapshot is captured, by `glyph`'s TeX subset on Latin Modern Math, and stored as outlines in `scene.lettering.json`. `MathTex` draws those outlines ([Maths](REFERENCE.md#maths)).
- **`transform` matrices on the model.** Every move rewrites points, because points are what traces, the verifiers and matching transforms read. The SVG serializer already writes shape-relative path data plus a `translate`, so a pure move keeps its `d` without a matrix in the model. It writes coordinates in thousandths of a unit, and a cubic whose controls lie within one thousandth of the thirds of its chord, as a straight segment's do, as `L`.
- **Raster images.** A bitmap has no points to morph, would be embedded as bytes, and would make frames depend on a decoder; everything on stage is paths and glyph outlines.

The fork deleted Lantern's Mermaid flowchart layout and its JSON document format. Diagrams come from Agentic Mermaid capture, and [scene outputs](SCENE-OUTPUTS.md) gives the outputs the JSON documents produced, from native scenes.

## Embedded browser fonts

Every page uses SFNT copies of the embedded Inter, JetBrains Mono and Noto subsets: the same glyphs and metrics, without the WOFF2 Brotli decoder. The faces a lettered page decodes of its own, subset cuts and outline-lettering subsets, are committed as WOFF2 and converted to SFNT when the page is built (`tools/lib/woff2.ts`, in JavaScript with Node's Brotli), so no page ships the decoder. `rayner check`'s bare runtime bundles the scene the same way. Authoring in Node keeps the full loader. `test/browser-fonts.test.ts` compares both loaders over fixed fallback examples and generated strings, and `test/woff2.test.ts` shapes every committed WOFF2 face and its conversion alike, character by character.

`npm run fonts` regenerates both. To rebuild only the browser copies from the committed subsets, run `node tools/repo/fonts-sfnt.ts` with fonttools and brotli installed in Python (`RAYNER_LETTERING_PYTHON` selects the interpreter); the tool checks the original shaper pin first. No Python runs when an author builds a page.

## What a page leaves out

A page whose scenarios show no diagram carries no diagram code: the build answers every import of `explain/diagrams.ts` with a stand-in (`tools/lib/explain-diagram-code.ts`) whose `Diagram` throws if it is ever reached, while the label helpers the close-ups and the checks read live in `explain/labels.ts`, which they import themselves, so `Diagram` and the Mermaid replay drop out of the bundle. The project decides it: some scenario made a diagram, from the snapshot store or from a snapshot of its own. Each scene counts the diagrams made on it (`diagramsOn`), and the command reads the scenes the project ran, so another collection in the same process never changes the answer. `rayner check` fails a diagram that only a reader's event at a live step draws, counted on the scenes its exploration ran, since such a page would carry no code to draw it. The page's style is minified, as its script is. `test/page-size.test.ts` holds both.
