# Look up an authoring feature

The [feature tour](https://oshineye.dev/projects/rayner/feature-tour) is an API demo, not a subject lesson. To write a complete scene that answers a question, follow the [tutorial](TUTORIAL.md), which builds an explainer of LRU and MRU cache replacement. For the local tour, run `npm run demos:build && npm run demos:serve` and open [feature-tour.html](http://127.0.0.1:5175/explainers/feature-tour.html).

The feature tour is one scene with 15 prebuilt cases. Choosing another feature starts at its first step, **Recipe**, even when you were viewing a Result. Transcript links also start at Recipe; a direct `?feature=camera&step=result` permalink still opens Result. Pick a feature, inspect the **Recipe** step for the *code an author writes*, then advance to **Result** to see that feature execute. Each case has a direct link, for example `feature-tour.html?feature=state&step=recipe`. The excerpts show author-side calls that produce the pictured behavior, but they are not complete standalone scenes. The tour's [runnable source](../scenes/explainers/feature-tour/scene.ts) adds imports, styling, positions and navigation between cases. They are not a second player implementation. In an installed project import the named classes/functions you use from `rayner` and import `stage` and `settingsOf` from `rayner/explain`; [the reference](REFERENCE.md) lists their options. `s` means `const s = stage(this);` **before** the steps in `construct()`; `this` is your `Scene`. Add an excerpt after the step whose picture it changes (unless it includes its own `this.step`). The `settings` recipe's `static settings` declaration belongs in the class body, not inside `construct()`.

**Scope:** this is a lookup of representative authoring families, not a course, a technical explanation or an inventory of every exported class, option, animation and diagram family. Do not mistake 15 example cases for exhaustive API coverage. The specialized features below have their own runnable examples and build-time prerequisites; a fabricated on-screen “demo” without those prerequisites would be worse than a link to the real source:

- **Additional writing systems, faces, weight and italic:** add `static meta = { id: 'alphabet', title: 'Αλφάβητο', lettering: { scripts: ['Grek'] } };` before drawing `new Text('Αλφάβητο')`; capture and commit `scene.lettering.json` as described in [Lettering](REFERENCE.md#lettering-on-request). Arabic, Devanagari and Hebrew, replacement faces and real bold/italic use the [outline workflow](LETTERING.md#supported-requests).
- **Played scores:** the [melody and rhythm scene](../scenes/explainers/melody-rhythm/scene.ts) draws both piano rolls from the note data supplied to `step.audio`. Play starts sound locally after a reader gesture; see [score audio](REFERENCE.md#optional-score-audio) for clip limits and cancellation.
- **Maths:** add `lettering: { math: true }` to `static meta`, then draw `new MathTex('x^2', {display: true})` using `s.enter(..., {describe: 'x squared'})`; supply the pinned Latin Modern Math font and run `rayner snapshots` before checking. See the complete [MathTex scene and commands](REFERENCE.md#maths).
- **Diagram families and geometry:** change `source` in `s.show({source: 'graph LR\nA --> B'})` to a supported family source; call `d.reveal`, `d.mark`, `d.dim`, `d.note`, `d.focus` or `d.morph` as the story requires. For natural font measurements set `s.show({source, lettering: 'natural'})`; it needs an appropriately requested face and refreshed snapshots. See [diagrams](REFERENCE.md#diagrams) and [measurements](LETTERING.md#diagram-measurements).
- **Native code diffs, matching keys, emphasis shapes, graph areas, copies and sequencing:** the [engine feature inventory](REFERENCE.md#engine-features) links the exact author-side constructor and an existing explainer for each. A test-only `viewMismatch` is a verification tool, not a reader-facing animation; use [view fidelity checks](VIEWS.md) to test your model-driven picture.

Neither a successful check nor this tour proves every explanatory claim true. The examples show API behavior and accessibility descriptions; independently test any domain model before publishing it. Keep the reader's actual question ahead of a feature inventory.

The result step clears the recipe so the code cannot obscure the demonstration. Keep the complete recipe available as its own step. For larger examples, compare [the latest-search guard](../scenes/explainers/latest-search/scene.ts), [the cache diff](../scenes/explainers/mr-cache/scene.ts) and [layout direction](../scenes/explainers/layout-direction/scene.ts). A feature example explains an authoring operation; a topic lesson uses that operation to answer a reader’s question.
