What is a statechart?

Step 1 of 14 · Definition

What a statechart is

The definition

A statechart is a state machine whose states can contain other states. It adds two things. A state can be a box of states, a parent, and any event its children don't handle goes to the parent. And a state can be split into regions, each in one state at the same time.

A state machine is always in one of a set of named states, and an event can move it to another. The two additions are easiest to see in pictures.

Step 2 of 14 · Vocabulary

Four words, then a light

Four words carry the whole lesson.

  • State: a situation the machine can be in, such as Off.
  • Event: something that happens to the machine, such as a button press. Events are written in capitals, like SWITCH.
  • Transition: an arrow from one state to another, labelled with the event that takes it.
  • Handle: a state handles an event when it has an arrow for that event. Without an arrow, the state does not handle it.
Predict A light is Off. SWITCH is pressed twice. Which state is it in?

Pick one answer first.

The first press moves the light to On, and the second moves it back to Off.

That is one press. The second press has an arrow in On as well, so it takes the light back to Off.

Nothing is lost. Each press has an arrow in the state the light is in at that moment.

Answer: Off. The machine answers each event with the arrow of the state it is in when the event arrives.

Step 3 of 14 · The problem

The problem: a flat coffee machine

A flat machine lists every state as its own box, with no boxes inside boxes. Here is a coffee machine drawn flat. Only its POWER_OFF arrows are shown.

Flat coffee machine: POWER_OFF arrows

Why that matters: in a plain state machine, behaviour shared by many states must be copied onto each of them. Give a coffee machine a power button, and idle, grinding, brewing and ready each need their own POWER_OFF arrow. Put the four in a box called on, and one POWER_OFF on the box does the job.

Predict How many POWER_OFF arrows does the flat machine need?

Pick one answer first.

One is what the boxed version needs. The flat version needs a copy on every state that can be on.

Idle, grinding, brewing and ready each need one. Off does not, because the machine is already off.

Off has no POWER_OFF arrow in the picture, because the machine is already off. That leaves four.

Without them, the machine could not be switched off from those states.

Answer: four. Every state that can be on needs its own copy. That copying is what a box removes.

Step 4 of 14 · The fix

Put the four in a box called On

A state can be a box. Idle, Grinding, Brewing and Ready now sit inside a box called On, and the box has one POWER_OFF arrow, to Off. None of the four has its own copy.

Predict The machine is Brewing, and POWER_OFF arrives. Brewing has no POWER_OFF arrow of its own. What happens?

Pick one answer first.

Nothing is lost. An event a state cannot handle moves up to the box around it, and that box is checked next.

Brewing has no arrow, so the event moves up to On. On has the POWER_OFF arrow, so the machine goes to Off.

That would be true if no box had the arrow. On does have it, so the event is handled there.

Answer: Off. An event travels up the boxes until a state has an arrow for it.

Step 5 of 14 · How events travel

Events travel up, innermost first

The rule

An event is offered to the innermost state first. Innermost means the smallest box around the state. If that state has no arrow for the event, the event moves up to the next box. The first state with an arrow handles the event, and the search stops there.

Common misconception

“The outer box gets the event first, so the box always wins.” It is the other way round. The inner state looks first, so it can override the box for one event.

Predict The machine is Brewing. TIMEOUT arrives, because nothing has happened for a while. Brewing has a TIMEOUT arrow to Ready, and On has a TIMEOUT arrow to Off. Where does the machine go?

Pick one answer first.

This is the common mistake. On is checked only after Brewing, and Brewing has already handled the event.

Brewing is offered TIMEOUT first. Its arrow handles it, so On never sees it.

One event gets one handler here. The search stops at the first arrow it finds.

Answer: Ready. The innermost state with an arrow wins. On still has its TIMEOUT arrow, but this event never reaches it.

Try it: TIMEOUT in Brewing (Reset returns to Brewing)

A child can override its parent for one event. The trace shows On has the arrow, but it is never asked.

Step 6 of 14 · Pattern

The same shape, somewhere else

A box is useful whenever one rule covers many states. Here a phone app has a box called Signed in around its Home, Settings, Editor and Help screens. LOG_OUT is drawn once, on the box.

Predict A Help screen is added inside Signed in. Does Help need its own LOG_OUT arrow?

Pick one answer first.

You would need one only if Help had to behave differently. Otherwise the box already covers it.

Help has no LOG_OUT arrow, so the event moves up to Signed in, which has one. A new screen inherits the box's arrows for free.

Position does not matter. Any screen inside the box is covered.

Answer: no. The box's arrows cover everything inside it, unless a screen has its own arrow for the same event.

Try it: the phone app (starts on Home)

The pattern in three places

  • Coffee machine: POWER_OFF on the On box covers Idle, Grinding, Brewing and Ready.
  • Phone call: HANG_UP on the In call box covers Ringing, Talking and On hold.
  • Game: PAUSE on the Playing box covers Level 1, Level 2 and the Boss fight.
Rule of thumb

If every state inside should react the same way, put the arrow on the box. If only one state should react, put the arrow on that state.

Step 8 of 14 · Flags

Booleans hide the same problem

Booleans hide the same problem: isPlaying and isPaused can both be true, which should be impossible.

A boolean is a yes-or-no flag, true or false. Two flags give four combinations, and nothing in the code stops the impossible one.

Predict Press Play, then Pause. What do the two flags say?

Pick one answer first.

That is what you would expect after Play. But Pause ran last, and it did not clear isPlaying.

Pause set isPaused, but nothing set isPlaying back to false, so it is still true.

pause() sets isPaused to true and leaves isPlaying alone, so both are true. That is the impossible combination.

Nothing in this code sets a flag back to false, except Reset.

Answer: both true. Each function sets one flag and forgets the other.

Try it: two flags, written the careless way

function play()  { isPlaying = true; }
function pause() { isPaused = true; }

Fixing this by hand means writing both flags on every path that changes playback. That works, but it depends on everyone remembering. Step 9 shows a structure where the impossible combination cannot be written.

Step 9 of 14 · Regions

Regions keep playback and volume apart

Regions keep playback and volume apart, as two small machines side by side, so the impossible combination can't be written.

Here the player is one box with two regions. Playback holds one state, Playing or Paused. Volume holds one state, Unmuted or Muted. You draw four states, and the machine can be in four combinations.

Predict Can the player be Playing and Paused at the same time?

Pick one answer first.

With two flags, yes. With regions, Playback is one small machine, and it can be in only one of its states.

Playback is one small machine, so it is in exactly one of Playing or Paused. The impossible combination cannot be written.

Muting belongs to the Volume region. It cannot change which state Playback is in.

Answer: no. A region is in one state at a time, and the two states of Playback are the only two it can take.

Try it: the player (starts Playing and Unmuted)

Try PLAY while the player is already Playing. Nothing handles it, so nothing happens. PAUSE is handled by Playback alone, and Volume ignores it.

Step 10 of 14 · Flattening

Flattening: nothing new becomes possible

Nothing new becomes possible: flatten any statechart and you get an ordinary state machine with the same behaviour. What you gain is a drawing the size of the idea instead of the size of every combination, so it stays readable as the product grows.

To flatten a statechart, list every combination the regions can be in, make each combination a state, and copy each arrow onto the states it applies to. The table below is made that way from the player you saw in step 9.

Answer: yes. Flattening copies the regions exactly, so the table and the regions always agree.

Step 11 of 14 · Myth

A myth to clear up

Myth

A statechart can do things a state machine can't.

Predict True or false?

Pick one answer first.

Look at step 10. Every statechart flattens into a plain state machine with the same behaviour, so nothing new is possible.

Flattening always works, so whatever a statechart does, a plain state machine can also do. It just needs more drawing.

Answer: false. Nesting and regions are a shorter way to draw the same machine.

The myth is wrong because flattening always works. Nesting and regions do not add behaviour. What they change is the size of the drawing, and that is their whole value.

A related idea

Regions are not extra processors. The machine still handles one event at a time. Regions are parts that always hold one state each.

Step 14 of 14 · Remember

The sentence to remember

A statechart is a state machine that can nest states and run parts side by side, so shared behaviour is written once and independent features don't multiply.

  • Nesting: put shared behaviour on the box. The innermost state gets each event first.
  • Regions: give each independent part its own small machine, so you draw the parts, not the combinations.
  • Flattening: the same behaviour, written out in full. It shows that nothing new is possible.
