# Why stealing an authorization code is not enough

- **Reader:** builds or reviews a mobile or desktop app that signs users in with OAuth through the browser; knows the app receives a code in a redirect and trades it for a token, and has heard of PKCE without knowing what it protects.
- **Answer:** Redeeming the code also needs the verifier, which never passes through the redirect
- **Changed condition:** whether the theft is replayed against PKCE. With it, the malicious app catches the redirect and its token request with a guess gets invalid_grant, and a live machine lets the reader play the messages in any order; without it, the explainer follows the legitimate exchange only, which still carries the challenge check. Either way the comparison it makes is the theft before PKCE (the code alone buys a token) against the same theft after the code is bound to a challenge.
- **Reader's own work:** predict, from the opening theft, what the server could ask for that the thief does not have; in the attacker scenario, send the sign-in’s messages in any order on the live machine and try to get the malicious app a token; answer the check questions, which ask about a fixed client secret, a thief who also reads the challenge, and the plain method.
- **Checked against:** RFC 7636’s appendix B example (that verifier’s S256 challenge) and node’s own SHA-256 (`node:crypto`), including padding boundaries, non-ASCII text and random strings, in `model.test.ts`, which also holds the token endpoint’s comparison and which channel carries each parameter to RFC 7636 §4 and RFC 6749 §4.1, and plays every order of the sign-in’s messages. No real authorization server is run.
- **Leaves out:** the code, client ID and redirect URI checks (assumed valid), ordinary token-request fields, a bound code presented with no verifier at all (RFC 7636 requires the parameter without naming the error), the plain method’s flow, a compromised client that leaks its verifier, other OAuth protections, and the malicious app’s own messages on the closing channel map.

## Check yourself

1. Why does the app not embed one fixed client secret in its program and send that with the token request instead?
   Every installed copy carries the same secret, so anyone can extract it from the program, including the author of the malicious app, and the server could not tell the copies apart. The verifier is made fresh for each sign-in and stays on the device until the client’s own TLS request.
2. Suppose the malicious app can also read the authorization request, so it holds the challenge E9Melh… as well as the code. Can it now redeem the code?
   No. The server wants a verifier whose S256 equals the challenge. Knowing the challenge does not produce such a verifier: finding one for a verifier made from 32 random bytes is computationally infeasible, so whatever the app sends still gets invalid_grant.
3. RFC 7636 also defines a plain method, in which the challenge is the verifier itself. Against the app in the previous question, what changes?
   It succeeds. The challenge it read is the verifier, so it can present the code with that verifier and get a token. Plain protects only when the authorization request itself cannot be read, which is why RFC 7636 requires clients that can use S256 to use it (§4.2, §7.2).

## Why this explainer

A native app is a public client: any secret built into it ships to every device and can be extracted, so the server cannot ask it for one. Another app on the same device can register the same custom URI scheme and catch the redirect. The explainer starts from that theft working, so the reader feels the problem before PKCE is named, and asks what the app that started the sign-in has that the app catching the redirect does not.

The answer is a secret made for this sign-in alone, and the takeaway is which channel each value crosses. The aha is the closing redraw by channel instead of by time: two lanes, the browser lane another app can read and the client’s own TLS lane. The code travels in both; the verifier only in the TLS lane, so an app that reads the browser lane holds the code without the value that redeems it. It also marks the boundary: an attacker who can read the app’s memory has the verifier too.

The opening theft is replayed after the code is bound to a challenge, so the changed requirement at the token endpoint is visible against the same picture. The no-attacker setting follows the legitimate exchange; it does not remove the challenge check. The challenge travels through the browser and is treated as public: SHA-256 makes recovering a verifier made from 32 random bytes impractical, though not a mathematical guarantee that no preimage exists. The example verifier and challenge are RFC 7636 appendix B’s; a real sign-in needs a fresh, unpredictable verifier. The sequence diagrams, the channel map and every server answer are drawn from the model’s messages, and the diagrams leave out token-request fields the comparison does not need; the opening caption names the client ID and redirect URI so the omission does not suggest they are unnecessary.
