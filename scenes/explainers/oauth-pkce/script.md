# Why stealing an authorization code is not enough

A mobile app signs a user in through the browser. When the user has consented, the authorization server sends a short-lived code back in a redirect to the app's custom URI scheme, and the app trades that code for an access token. Another app on the same device can register the same scheme, and the operating system may hand it the redirect instead. The legitimate app is a public client: it ships to every device, so any secret built into it could be extracted, and the server cannot ask it for one. In the unprotected exchange the malicious app presents the stolen code, with the client ID and redirect URI that anyone can read, and gets a token. What could the server ask for that the app which started the sign-in has and the app which caught the redirect does not?

The answer is a secret made for this sign-in alone. Before the redirect, the legitimate app generates 32 random bytes, encodes them as the code verifier and keeps them. It sends the server a value derived from the verifier, the code challenge: with the S256 method, the base64url encoding of the verifier's SHA-256 hash. The server stores the challenge with the code it is about to issue. Redeeming that code now needs the verifier, and the verifier never passes through the redirect. The scheme is PKCE, Proof Key for Code Exchange (RFC 7636).

The challenge does travel through the browser, so treat it as public. That is safe because the hash runs one way: given a verifier made from 32 random bytes, finding any value whose SHA-256 is its challenge is computationally infeasible. The verifier itself goes by a different route, the client's own TLS connection to the token endpoint, and only at the end.

Now replay the theft. The malicious app catches the same redirect and gets the code, but the token request must carry a verifier, and it has none, so it sends a guess. The token endpoint hashes the guess with S256 and compares the result with the challenge stored with the code. They differ, and the server answers invalid_grant instead of a token.

The legitimate app sends the code with the verifier it kept. The server runs the same calculation, finds the values equal and returns the token. The server never needed the secret in advance: the challenge it stored earlier let it recognise the right secret when it arrived.

So the useful question about each sign-in value is which channel it crosses. The challenge and the code cross the browser and the redirect, where another app can read them; the verifier stays on the device until the client's own TLS request. PKCE's protection rests on that separation. An attacker who can read the app's memory, and so obtains the verifier as well as the code, defeats it: the server would then see the right verifier from the wrong app.
