# What does your agent do when the Company says no?

- **Reader:** a developer who has followed the jacket exchange through chapter 1 (the seal says who is asking, the key says what your account allows) and now wants to know what a Poppy agent does when a request comes back refused, without reading section 7's error table and the six sections it points to.
- **Answer:** Each refusal’s code names its own remedy, and the agent applies that one: the wrong one loops, or throws away a good token
- **Changed condition:** what broke before the exchange was sent. An expired token, a read-only approval, an expired delegation, an ended Session, an old copy of poppy.json, sending too fast, and a key cut for the wrong service each come back with their own status and code, and each takes a different remedy; the reader should be able to name the remedy from the status and the code alone.
- **Reader's own work:** at the first step, predict the agent's next move from a refusal slip; at each later step, predict before the remedy plays; at the last step, break the errand seven ways, say which remedy you expect, press Agent answers, and read on the rail which remedy was applied and why the tempting one would have failed.
- **Checked against:** the Personal Agent Protocol draft 1.0 (in progress; as published on 2026-11-13), read and not run: `model.test.ts` holds the model to section 7's error table and the rules of sections 3.3, 3.4, 4.4, 4.5, 4.7, 5.3, 5.5 and 5.6, and 1.0's rule in 8.13 that an error code the agent does not recognize is handled by its status, each test naming its section, and `answers.ts` computes the answers below from the model. There is no reference implementation here to run the model against. It is also held to what the protocol itself publishes, copied on 2026-11-13 into `fixtures/poppy-official.json`: every error the model sends in a JSON body passes the Company kit's error schema, and its extension_required and version_unsupported bodies are spec.md's examples.
- **Leaves out:** time (token lifetimes, the clock behind Retry-After, how long a Company remembers an ended Session), real signatures and delegations, DPoP, session_ended for an account change in a Session (5.4), conversations carrying over to a new Session (8.11), fetching a website page again without the header (5.2), the order in which a Company checks one request against several faults (the draft does not give one), any remedy for extension_required beyond the model's own reading (the draft names none), and a real MCP tool: the sizing call that reads past orders, and its need for orders:read, are the model's assumption (the draft's example MCP server does "product search and sizing" and names no tool).

## Check yourself

1. Your agent's exchange comes back 400 invalid_session because its delegation has expired. What does it do, and why not start a new Session?
   It stops sending the exchange and fixes the cause: a new delegation, in the same Session, so the cart is kept. A new Session would carry the same broken header and get 400 invalid_session again.
2. Why are Session errors 400 rather than 401? What would go wrong if session_ended were a 401?
   An OAuth library treats a 401 as a bad access token, so it would throw away a valid token, and the agent would refresh or ask you again for nothing. With 400 the library keeps the token.
3. After session_ended, the agent starts a new Session and sends the exchange again, and that also gets session_ended. What now, and what did the new Session cost?
   It stops sending the exchange: the new Session got session_ended too, and the agent sends again once. The first Session’s cart did not carry over.
4. The agent calls the MCP server with its everyday token and gets 401 invalid_token with a resource_metadata URL. What does it do?
   It reads the metadata, refreshes for a token with resource https://mcp.example.com/mcp, and uses that token only at the MCP server. Its everyday token keeps working at the API.
5. You signed out of example.com yesterday. Today the agent's exchange gets a 401 with no error code, naming orders:write. Does it ask you to sign in?
   No. A 401 with no code is handled as insufficient_scope, and after you sign out the agent continues signed out: it asks you to sign in again only if you ask it to.

## Why this explainer

Chapter 1 showed one refusal, the 401 that taught the reader a seal is not a key, and moved on. A real agent meets eight kinds of no, and section 7 lists them in a table whose right-hand column is the interesting part: every row tells the agent what to do next, and no two rows tell it the same thing. That is what I want a reader to leave with. A refusal in Poppy is not a dead end and not a prompt to try again; it is a slip handed back with the ticket, saying what to bring next time.

So the picture is the returned ticket. The agent's request goes out along its lane carrying chapter 1's two marks, the wax seal and the brass key, plus a small tab for its Poppy-Version, and when the Company refuses it the ticket comes back with a slip pinned to it. The slip's number points at the part of the ticket that was wrong: a 401 or 403 at the key, a 400 at the seal or the version tab, a 429 at the clock. The code under the number names the remedy, and the remedy arrives as an object from where it really comes from: a newly cut key from the Company's sign-in desk, a fresh seal pressed by the agent, a new copy of poppy.json from the Company's door, an hourglass that has to run out. Then the same ticket goes again and rests on its stop.

The turn I am building to is the three 400s. By the fourth step the reader has learned that the number tells you which object is at fault, and expects the number to be enough. Then three slips arrive that all say 400 and each needs something different: invalid_session needs the agent to fix its own header, in the same Session; session_ended needs a new Session; version_unsupported needs a fresh poppy.json, and a new Session only if that changes the version. The number says "the seal"; the code says what to do about it. The step that follows asks why these are 400 at all, and the answer is the most practical sentence in the section: an OAuth library that sees 401 throws the token away, so a Session error dressed as 401 would cost a perfectly good key.

The "once" rule gets its own beat, because it is the rule that stops the agent and the Company from bouncing a request between them forever. The model's test runs an agent that ignores it against a Company that ends every Session, and the run only ends when the test's limit does.

The live step is a switchboard. The reader breaks the errand one of seven ways, the Company answers, the reader predicts, and presses Agent answers. My first design gave each of the six remedies its own button and refused the wrong ones with the draft's reason; thirteen buttons do not fit a phone, so the reasons moved into the picture instead. When the agent answers, the remedy rail lights the one remedy applied and strikes through the one a careless agent would reach for, and the panel under the ledger says why that one would fail; the picture's description carries the draft's full reason ("a new Session does not fix invalid_session: the same header fails in any Session"). Which wrong remedy counts as the tempting one is my choice, recorded in the model as `TEMPTING`. Two parts of the chapter are not on the rail and get their own words: the 400-versus-401 question, which is about OAuth libraries rather than the agent and gets a step of its own, and the once rule, which needs a Company that misbehaves and lives in the captions and the model's test.

What I left out: extension_required appears in the steps as the second 403, the one that is not about the key, but the draft gives no remedy for it, so the model's remedy (declare it in a new Session, since a Session's declared extensions are fixed) is marked as a reading. The order in which a Company checks a request that is wrong in several ways is not in the draft either; each trouble in this chapter breaks one thing.
