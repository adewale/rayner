# How do I write that in Rayner?

- **Reader:** someone choosing or starting to write Rayner explainers, who can read TypeScript and knows what they want on the page (a setting, a code panel, a morph, a chart) but not which lines produce it or what those lines leave behind.
- **Answer:** Each feature takes a few lines of the scene, and the picture they leave at rest is what a reader who opens the step from a link sees
- **Changed condition:** none in the sense of one outcome changing. The Authoring feature setting picks one of twenty-nine scenarios, each a different feature; the comparison each makes is between the motion and the resting picture it leaves (a before panel on the left, the result on the right; the camera scenario uses a ruler instead).
- **Reader's own work:** each recipe step asks for a prediction about what its lines leave at rest, answered by the result step; the reader picks which feature to inspect; the three check questions transfer the idea to a second morph, a second object outside the camera's view, and reader-typed data.
- **Checked against:** Nothing external: the subject is Rayner itself. The build rule (one scenario per option) and the drawing tool's trace rule have tests (`test/explain-gates.test.ts`, `test/explain-stage-tools.test.ts`); `test/explain-onboarding.test.ts` checks each scenario's recipe shows exactly its `RECIPES` lines before a non-empty result; `test/explain-fidelity.test.ts` checks the state scenario's count and the camera's framed width. The result pictures are the evidence for the rest.
- **Leaves out:** complete API coverage: the scenarios are short demonstrations. The direction scenario lays out Latin text right to left and does not show shaping a right-to-left script. The before panels, the camera ruler and Restore's dashed outline are this scene's own artwork, not produced by the recipe lines shown.

## Check yourself

1. Run the code-edits recipe twice in one step: count += 1 becomes count += 2, then count += 3, each morph with markAdded. What does a reader who opens that step from a link see, and is there any sign of count += 2?
   Two lines, let count = 0 and count += 3, with count += 3 marked as added. The second morph fades count += 2 out along with its mark, so nothing in the resting picture shows that it existed; to keep it, draw the earlier panel beside the result, as the before panels on this page do.
2. In the camera scenario, the author also enters a second circle at (5, 0) before calling s.focus(subject). Is it in the result picture, and where is it?
   It is out of the picture. The closer view frames 6 of the stage’s 16 units around the first circle, roughly x = −3 to 3, so a circle at x = 5 falls outside it. It is still at (5, 0), because s.focus moves only the camera, and s.focus(‘all’) would bring it back into view.
3. An author wants the chart scenario to plot numbers that each reader types into a box. Can a Rayner page do that, and what can the author offer instead?
   No. A reader can only choose among the options a setting declares, and the build makes one scenario per option before anyone reads the page. The author can declare a setting whose options are a few prepared data sets, so each one is a scenario the build makes and the author can read.

## Why this explainer

An author choosing Rayner asks "how do I write that?" one feature at a time, so each scenario pairs the few lines an author writes with the picture they leave. The idea every scenario carries is that code describes what happens over time, while a step opened from a link has to explain the state it leaves behind: Transform leaves only the square, a matching morph leaves only the new text, a code morph leaves only the current line, and a camera move changes the view, not the object's coordinates. When the motion is the point, the author has to draw what the reader needs at rest.

That is why the result step draws its own before panel, and why the page must not let readers attribute it to the feature. The starting copies, the camera ruler and the dashed outline are added artwork; the glyph correspondence under the matching example comes from the actual matched pairs, so it can be inspected after the motion. The camera changes the whole view, so a before panel would sit inside the closer view too; a ruler across the stage, showing only its middle after the focus, makes the change visible instead.

The tour doubles as coverage. Between them the scenarios run every scene-facing name a guide teaches that no other explainer uses (`ArcBetweenPoints`, `Brace`, `Underline`, `NumberLine`, `DecimalNumber`, `MathTex`, `MoveAlongPath`, `Write`, `TransformFromCopy`, `TransformMatching`, `diffLines`, `parseUnifiedDiff`, `smooth`, `bars`, `between`, `palette`), so `rayner check` exercises each. Keep that true when adding or removing a scenario. The palette scenario builds its stage in nord and the rest in github-dark; the rate-function ticks are computed from the same functions the dots move by. Changing the feature returns to its recipe (`scenarioNavigation: 'first'`), while a direct link to a result still works.

Each result step's evidence is declared in `scene.review.json`: the words a caption points at, and, by key with `paint: "stroke"`, the ink that carries the point where the scene draws it by hand (the square, the restored circle and its outline, the box round 42, the chart's line, the drawn path). Automatic emphasis covers the helpers' own marks (a walked trail, a focused or added code line); these are the subjects it cannot infer.
