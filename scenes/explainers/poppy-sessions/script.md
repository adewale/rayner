# What is inside the seal?

- **Reader:** a developer who has seen chapter 1 (the seal is the Session header, which says who is asking; the key is the access token, which says what the account allows), knows OAuth roughly, and now wonders how a shop can trust a seal from an agent it has never met, and know which User it is for without learning who that User is.
- **Answer:** Three links: the agent's URL publishes its keys, one vouches for a short-lived key, and that key seals each request
- **Changed condition:** whether the Company remembers what it has verified (the jti of each header, and the User ID each delegated key signed for), which the draft allows and does not require. Remembering, an exact copy sent ten seconds later is refused as a copy, and a leaked delegated key used for another User is refused; not remembering, the copy gets 200 and the leaked key's request is accepted as that User, signed out, and gets 401. Every other tamper is refused either way, by the same check.
- **Reader's own work:** before each refusal, predict which check stops the copy; switch "The Company remembers" and predict which two answers change; at the last step, tamper with the URL, the audience, the signer, the token and the clock themselves, and read which check refuses each, with the draft's reason.
- **Checked against:** the Personal Agent Protocol draft 1.0 (in progress; as published on 2026-11-13), read and not run: `model.test.ts` holds the model to the rules and examples of its sections 4.1, 5.1, 5.2 (including Delegated keys), 5.3, 10.4 and 10.7, each test naming its section; once a header is verified, chapter 1's model decides what the account allows. There is no reference implementation to run against, and no real cryptography: a signature in the model is the name of the key that made it. It is also held to what the protocol itself publishes, copied on 2026-11-13 into `fixtures/poppy-official.json`: its delegations and Session JWTs have the claims and typ values of the Company kit's JSON Schemas and none the delegation schema forbids, and the values of spec.md's 5.2 examples; only the shortened keys, IDs and stand-in hashes fail the schemas' formats.
- **Grounding:** read: the Personal Agent Protocol draft 1.0, as published on 2026-11-13
- **Leaves out:** real signatures (ES256, PS384, JWK thumbprints), fetching documents over HTTP and section 3's address checks, operator signatures (Web Bot Auth) beyond a sentence, blind signing (10.7), which keeps the agent's own systems from learning which Companies a User uses, DPoP, Session lookup and ended Sessions, website pages, Agent IDs beyond a sentence, caching delegations and rotating published keys.

## Check yourself

1. A thief copies your whole exchange request, Session header and access token together, and sends it to GET /orders/ord_7Hk2 to read the order instead. What does example.com answer, and which claim stops it?
   400 invalid_session at htm and htu: the header was signed for POST /orders/ord_7Hk2/exchanges, and this is GET /orders/ord_7Hk2. A Session JWT covers one request, and only that one.
2. shoes.example's own documents named example.com's cart URL, so the agent signed a header for that URL and sent it to shoes.example, which replays it at example.com. Every signature in it is genuine. What happens?
   400 invalid_session at aud: the header is addressed to https://shoes.example, and this is https://auth.example.com. The agent names the Company it verified in aud, so a header one Company collects is refused by every other.
3. Your delegated key leaks while its delegation still has hours to run. What can whoever holds it do at example.com, and until when?
   Sign headers as any User ID it knows, signed out only: the exchange gets 401, naming orders:write. A Company that remembers which User ID each key signed for refuses it for anyone but usr_Q7c1vK: key 9E421cSq has already signed for usr_Q7c1vK. At 07:00 nothing works: the delegation expired at 06:00:00, and it is 07:00:00.
4. An exact copy of the agent's request arrives ten seconds after it, and another two minutes after it. What happens to each?
   Where the Company remembers jtis, the copy ten seconds later gets 400 invalid_session (jti e1j3Vb has been seen already, so this is a copy); where it does not, 200. The copy two minutes later gets 400 invalid_session either way: the header was signed at 00:13:20, 120 s before 00:15:20, outside the 60 s window (section 5.3).
5. Why does the agent sign your requests at example.com (usr_Q7c1vK) and at shoes.example (usr_m4Tz9P) with different delegated keys?
   With one key, the two Companies could match you by its thumbprint or its delegation’s jti. With 9E421cSq at one and Lp0wF2Ux at the other they have nothing in common, and a leaked key exposes you at one Company only.

## Why this explainer

Chapter 1 drew the Session header as a seal and asked the reader to take it on trust: the agent signs, the Company checks. A developer who has used OAuth will not take it on trust for long. The Company has never met this agent, holds no shared secret with it, and is meant to learn which User a request is for without learning who the User is. So the question here is the one that seal invites: what is pressed into it, and why would anyone believe it?

The draft's answer is a chain, and I want the reader to see it as one: the agent's client_id is the address of a document that publishes its keys; one of those keys signs a delegation, a pass that lasts at most a day and names a second key; that second key seals each request. Two signatures and an address. The reader should be able to say why there are three links rather than one. If the published key signed every request, it would sign things naming a User and a Company, so the one key every Company trusts would also be the one record of where every User shops, and losing it would expose everyone. A delegation names nobody, and a delegated key signs for one User ID, so a leak exposes one User at one Company, and only until the pass expires.

The second half of the insight is that every claim inside the seal is there to stop one particular copy. That is why the chapter is built as a game of forgeries rather than a list of fields. The reader holds a genuine sealed request and changes one thing at a time: sends it to another URL (htm and htu stop it), replays a header another Company collected (aud), wraps a copied token in another agent's seal (the token was issued to the agent that must sign), signs with the published key directly (there is no delegation), waits (iat; a delegation that expired), sends it twice (jti, if the Company remembers), uses a leaked key for someone else (one User per key, if the Company remembers). Each refusal names the check and gives the reason in the draft's terms. By the end, the claims are no longer a list to memorise; each has a reason the reader has watched it serve.

The setting is the one lever whose other option changes conclusions: the draft makes two of these checks optional. With them off, an exact copy inside the minute goes through, which is the honest limit the draft states ("a copied one works only for the same method and URL, and only briefly"), and a leaked key gets as far as acting for another User signed out, which still reaches no account. I would rather the reader see that than believe the seal is airtight.

The chapter reuses chapter 1's model rather than copying it: the claims come from its `sign`, and once this chapter's checks pass, its `answer` decides what the account allows, so a verified header with no token still gets chapter 1's 401. The User IDs, the agent, the thief, the Session ID and the exchange are chapter 1's.

What I left out, and why. Real cryptography cannot run synchronously in a page model, so a signature is the name of the key that made it, and the model assumes nobody can write another key's name; that is the property ES256 provides, and saying so is better than pretending. Operator signatures (Web Bot Auth) get a sentence, because they let a network edge recognise the operator but the draft is explicit that they replace nothing here. Blind signing is real and clever, and it answers a further question (could the agent's own servers learn which shops a User visits?), which deserves its own explainer. Agent IDs follow the User ID's rules and get one sentence.
