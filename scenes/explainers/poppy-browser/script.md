# How does the agent's browser join the Session without ever carrying the key?

- **Reader:** a developer who has read chapter 1, so knows the seal (the Session header: who is asking) and the key (the access token: what the account allows), knows OAuth roughly and what a cookie and a cross-site form post are, and now wonders how an agent that drives a real browser on a shop's website fits into the same Session.
- **Answer:** The agent authorizes its browser's one-time code in a request of its own; the code works only with the cookie set in that browser
- **Changed condition:** what the agent's key allows. Signed in with poppy:browser-sign-in, the browser joins signed in to the User's account; signed out, it joins the same Session signed out; signed in without that scope, step 2 is refused with 403 insufficient_scope, and the agent authorizes the same code again without its key, so the browser joins signed out. And who sends which half: a code without its cookie, or a cookie whose code no agent authorized, opens nothing.
- **Reader's own work:** predict what the shop can read from a browser (cookies, not the agent's headers); predict which browser may submit the code before the cookie is shown; at the attack steps, say which half the attacker is missing before the Company answers; at the last step, play the attacker and the agent in any order (submit before authorizing, browse before joining, forge a form from another site, send the agent a code by message) and read why each press fails or is refused.
- **Checked against:** the Personal Agent Protocol draft 1.0 (in progress; as published on 2026-11-13), read and not run: `model.test.ts` holds the model to the rules and examples of its section 6 (each of the four steps, the cookie and page rules, poppy:browser-sign-in, web.unscoped, web.disabled, the login table), 10.6 and the page-fetch rule of 5.2, each test naming its section. The Session header checks are chapter 1's model, imported. There is no reference implementation here to run the model against.
- **Grounding:** read: the Personal Agent Protocol draft 1.0, as published on 2026-11-13
- **Leaves out:** time (the code's and the join cookie's short life, Max-Age 60, so nothing expires in the story), real randomness and signatures (codes, cookie values and keys are fixed names), how a real browser enforces SameSite, frame-ancestors and COOP (the model recognises the guide-suggested values and states which attack each missing value opens), the software that keeps the code out of the model's context (10.2), Mediated Sign-In beyond who decides the scope, and an agent that joins again to change scopes.

## Check yourself

1. An attacker authorizes a code in its own signed-in Session, then a page on evil.example makes your agent's browser post that code to example.com. What comes back, and which half is missing?
   An error page and no Session cookie: the form came from evil.example, so the browser sent no join cookie. The code was authorized, but it arrived without its cookie.
2. A message to your agent says: here is your code. What does your agent do, and what happens when the attacker's browser, which loaded that code, submits it anyway?
   It declines: a code from a message may come from someone else’s browser, and the agent authorizes only a code its own browser loaded. The attacker’s browser has the cookie, but it gets an error page, since no agent authorized the code.
3. Your agent is signed in, but its token lacks poppy:browser-sign-in. What does step 2 answer, and how does the browser still join?
   403 insufficient_scope, naming poppy:browser-sign-in. The agent authorizes the same code again without the token, and the browser joins the Session signed out.
4. The agent's browser was already logged in as B on the website, and joins with a token for account A. How does it browse, and what is it once the Session's sign-in ends?
   It browses signed in to A, with the token’s scopes. When the Session’s sign-in ends it is signed out: the login as B does not come back.
5. While its browser is joined and signed in, the agent fetches a help article with its own HTTP client. What does that request carry?
   The Session header alone, with no access token and no token hash in it, so the request is signed out.

## Why this explainer

Chapter 1 drew the website as one lane and the browser's join as one request, and said the access token does not pass through the browser. A reader who stops to think finds that hard to believe. A browser cannot carry the agent's Session header, because the agent does not write its headers; it can carry cookies, but a cookie that the Company hands to a browser is exactly the kind of credential anyone could plant in someone else's browser. So the question is concrete: how does the Company get a browser into the right Session, signed in to the right account, when the only proof of the User's consent is a key the agent must never let out of its own hands?

The answer is two halves that only meet in one place. The Company's page gives the browser a one-time code to read and, in the same response, a cookie the browser keeps and no page can read. The agent takes the code to the Company in its own request, under its seal and with its key, and the Company stamps it: authorized for this Session, this account. Only then does the browser hand back the code with the cookie, and the halves are matched. The insight I want to land is that each check is passed by exactly one party. Only the browser that loaded the page holds the cookie. Only the agent can stamp the code, because only it can sign for the Session and hold the key. The key goes from the agent to the Company and nowhere else.

The visual idea is a ticket torn in two at the Company's counter. The stub with the printed code goes into the browser window, where the agent reads it; the other half, the cookie, goes into the browser's jar, out of the page's reach. The tear's profile is the match: a stamped code that arrives with the wrong half, or with no half at all, visibly does not fit. That gives the two attacks a shape before they have names. In the first (the login cross-site request forgery of RFC 9700), the attacker's stub is stamped, in the attacker's own Session, but it arrives in the agent's browser from another site, and the browser sends no cookie with a cross-site form; the stub comes without its half. In the second (consent phishing), the attacker holds the right half in its own browser and needs the User's agent to stamp its stub, so it sends the code in a message; the agent stamps only a code its own browser loaded, and the half arrives with an unstamped stub. Each attacker holds one half and lacks the other, and that symmetry is the aha.

The second attack is the honest place to admit a limit: the Company cannot tell the difference. If an agent did authorize a code from a message, the attacker's browser would join the User's Session, signed in. The model shows this (a test runs the careless agent), and the caption says so: that check is the agent's discipline, and it is why the draft writes it as a MUST.

The setting is the key. Signed in with poppy:browser-sign-in, the browser browses signed in. Without that tooth on the key, step 2 is refused and the agent comes back without the key, and the browser joins signed out: the same Session, no account. Signed out, the same. I chose this lever over a "browser was already logged in" setting because it changes what happens at the moment the key is used, which is the chapter's subject; the table of earlier logins is a comparison of four rows, better seen at once than one row per scenario, so it gets one picture of its own.

The first step is the contrast with 5.2: fetching a help page with the agent's own HTTP client carries the seal and never the key, signed out, even when a browser is signed in. That sets up why a browser needs a different way in, and web.disabled fits there as the Company's request not to browse at all, which the protocol cannot enforce.

The last step is live and ends the story finished, so the reader starts from the beginning and can do things out of order: submit before authorizing (the code is spent, start again), browse before joining (refused, with the reason), and both attacks once the browser has joined. The attacks wait for the join because the state space has to stay small enough to check every state; the model's own tests show the forged form fails the same way before a join.
