# How does an agent know a poppy.json speaks for the shop?

- **Reader:** a developer who has seen chapter 1, or knows roughly that a Personal Agent reads a shop's poppy.json before it does anything there, and who now asks the next question: anyone can write a JSON file, so why should the agent believe this one?
- **Answer:** The domain names its issuer and the issuer lists the domain back, and each check stops one way to impersonate the shop
- **Changed condition:** who serves the document. The real shop's file passes all four checks; a copy on a lookalike domain stops at the domain check; a domain that names example.com's issuer stops at the issuer's listing; an uploaded file reached by a redirect stops at the path check; a small shop with no issuer passes with signed-out Sessions only; the real shop on a day its metadata times out stops at the issuer check.
- **Reader's own work:** before each forgery's checks run, predict which of the four checks will refuse it; at the last step, choose who serves the document and run the checks one at a time, reading why a press after a refusal, or after the last check, is refused.
- **Checked against:** the Personal Agent Protocol draft 1.0 (in progress; as published on 2026-11-13), read and not run: `model.test.ts` holds the model to the rules and examples of its section 3 (discovery, HTTPS and redirects), 3.1 (fields), 3.2 (OAuth server), 3.3 (extensions, in outline), 3.4 (versions) and 10.3, each test naming its section. There is no reference implementation here to run the model against; the web is a table of answers in `model.ts`. It is also held to what the protocol itself publishes, copied on 2026-11-13 into `fixtures/poppy-official.json`: every metadata document in that web passes the Company kit's JSON Schemas, its documents give the values of spec.md's examples, and `discover` accepts the example documents themselves.
- **Grounding:** read: the Personal Agent Protocol draft 1.0, as published on 2026-11-13
- **Leaves out:** the network itself (TLS, timeouts as time, caching, the rule against private and loopback addresses), the issuer metadata's sign-in fields (token, revocation and grant types), scope descriptions and hints, auth.disabled beyond "no sign-in", the access hint beyond signed_in, what happens to User IDs and Sessions when a Company's identifier changes, and the inside of extensions.

## Check yourself

1. A lookalike domain, examp1e.com, serves an exact copy of example.com's poppy.json at its own well-known path. Which check refuses it, and why?
   The domain check: the document names example.com, and examp1e.com served it. A poppy.json speaks only for the host that served it.
2. evil.example serves its own poppy.json, honestly naming evil.example, and its protected resource metadata names https://auth.example.com as its issuer. What stops it, and what would it get without that check?
   The listing check: https://auth.example.com does not list https://evil.example. Without it, evil.example would be the same Company as example.com, and the agent would use User ID usr_Q7c1vK and example.com’s tokens there.
3. Someone uploads a poppy.json naming example.com to example.com/uploads/, and makes deals.example's well-known URL redirect to it. Why does only one check catch this?
   The last URL is on example.com, the uploaded file names example.com, and https://auth.example.com lists https://example.com, so the other three checks pass. Only the path check refuses it: the last URL, https://example.com/uploads/poppy.json, is not at /.well-known/poppy.json.
4. The agent has used example.com before. Today example.com's protected resource metadata times out. May the agent treat example.com as a Company with no issuer until it answers?
   No. The agent stops at the issuer check: the protected resource metadata timed out, and the agent does not fall back to the domain after an error. Falling back would make the Company https://example.com instead of https://auth.example.com, with new User IDs.
5. example.co.uk serves its own poppy.json, and its metadata names https://auth.example.com, which lists it. What User ID does the agent use there?
   usr_Q7c1vK, the same as at example.com: the two domains share the issuer https://auth.example.com, so they are one Company.

## Why this explainer

Chapter 1 spends one step on discovery: the agent reads a file, four lanes appear. A reader who stops to think about it finds the obvious hole. A JSON file is the easiest thing on the web to forge, and this one tells the agent where to send a User's tokens. So the question here is the sceptic's: what makes the agent believe it?

The draft's answer is four small checks, and on the page they read as a list of MUSTs. Read as a list, nothing says why there are four and not two, or why the path has to be exact, or why the issuer has to repeat something the domain already said. Each one becomes obvious the moment you try to get round it. So the explainer is built as a sequence of forgeries, each one a little cleverer than the last, and each stopped one gate further down. The copy on a lookalike domain is the forgery anyone thinks of first, and the domain check stops it: a file speaks for whoever served it. Draft 1.0 states the limit of that in 10.3: a lookalike that writes its own file, under the real shop's name and logo, passes every check, because the domain, not the letterhead, is the Company's identity, and the copy step's caption says so. The forger's next move is to serve a file that is honest about its own domain and point at the real shop's issuer, to become, as far as the agent can tell, a second domain of the same Company; the issuer's listing stops that. The cleverest is the upload: get a file onto the real domain somewhere, and redirect to it. It passes the domain check and both halves of the handshake, because it really is on example.com and example.com really does use that issuer. Only the exact-path rule stops it. That one is meant to surprise.

The model makes each of those claims testable rather than asserted. `discover` can run with one check skipped, and the test shows, for each forgery, that it is refused at its own check with every other one skipped too, and accepted, as example.com's Company with its User ID, when only its own check is skipped. That is the "each check stops one forgery" claim in the form the reader can check: no check is redundant, and none covers for another.

The aha I want is the handshake: a domain names its issuer, the issuer names the domain back, and only the two together make a link. The picture draws it as two arrows between a shopfront and the issuer's register, and the claim forgery is the one where the second arrow has nowhere to land. Section 10.3 adds the caveat that keeps this honest, and the last steps carry it: the check is two-way, but it does not make the issuer more trustworthy than the domain, because the domain chooses its issuer. Whoever controls example.com's well-known path speaks for example.com, as whoever controls its website does today.

The two quieter cases are there because they are where implementations go wrong. A small shop with no issuer is legitimate, and gets signed-out Sessions only. A real shop whose metadata times out looks, to a careless agent, exactly like that small shop; the draft forbids falling back, because the fallback would quietly change the Company's identifier and with it every User ID. Several domains sharing one issuer is the positive form of the same rule, and ends the story on a passing case the reader can then try to break.

Versions and extensions get a sentence each. They matter for whether the agent can use a document, not for whom it speaks, except for one rule that is the path check again: a version's document must be on the same host, so supported_versions cannot be used to point at an upload.

What I left out is mostly the network itself. The model's web is a table of answers; a timeout is an answer in it. It does not model the ban on private and loopback addresses, caching, or what an agent must do with User IDs when a Company's identifier changes. Two readings of the draft are the model's own and are marked where they are made: a 404 does not count as "explicitly establishing" that a known issuer was removed, and redirects are capped at five.
