Where does an empty ext4 filesystem's space go?

You format a "1 TB" disk, mount it, run df -h, and see 916G size and 870G available on a filesystem holding nothing. It is natural to blame the filesystem's own bookkeeping. That bookkeeping is part of the answer, but on a typical disk it is the smallest of the three parts.

The short answer, for a 1 TB disk with default mkfs.ext4 settings:
  1. About 7% is a change of units, not lost space. The box counts in GB (109 bytes). df -h counts in GiB (230 bytes) but labels them "G". 1,000 GB is 931 GiB. Nothing has been used yet.
  2. 5% is reserved for root, and it is not used either. ext4 sets aside 5% of blocks that only root (or a chosen user or group) can write to. df leaves them out of Avail but doesn't add them to Used. That is why Size − Used ≠ Avail. On 1 TB that's about 47 GiB, and you can shrink it in a second with tune2fs -m.
  3. About 1.7% really is the filesystem's own structures. Nearly all of it is the inode table, which is allocated up front for every file the filesystem could ever hold (1.56% with the defaults). Then there's a 1 GiB journal. Superblocks, group descriptors and bitmaps add up to less than 0.02%.

How df builds its three numbers

A lot of the confusion comes from the way the kernel fills in statfs() for ext4. Metadata and the reserve are handled differently, so they show up in different places:

The quick check: on a fresh ext4 filesystem, Size − Used − Avail is the root reserve (plus a fixed reserve of at most 16 MiB that ext4 keeps for delayed allocation). It is not metadata. You can't see the metadata in df output at all. It shows up only as a gap between the partition size and Size.

This is also why Use% can climb past 100% for root, and why a "full" disk still lets root write. df computes Use% as Used ÷ (Used + Avail), which leaves the reserve out on purpose.

What the structures actually are

ext4 splits the partition into block groups of 32,768 blocks, which is 128 MiB with 4 KiB blocks. A 1 TB disk has about 7,450 of them. Each group gets a fixed set of metadata, decided once at mkfs time:

The inode table dominates because ext4 decides how many files you can ever have at format time. By default that's one inode for every 16 KiB of capacity, and every inode is paid for whether you use it or not. On a volume that will hold large media files, backups or VM images, most of those inodes will never be used. df -i shows how many you've used.

One side effect: right after the first mount you may see the disk busy even though nothing is happening. That's the kernel's ext4lazyinit thread zeroing those inode tables in the background, because mkfs skipped writing them to save time.

Getting some of it back

Here's what you can change, from the most recoverable space to the least:

Reserved blocks: instant, safe, reversible on a mounted filesystem. The reserve is there so that root and system daemons can still write logs when a disk fills, and to give the allocator room to avoid fragmentation. That matters on / and /var. On a large data-only volume, 1% or even 0 is a common choice.

# see the current reserve
sudo tune2fs -l /dev/sdb1 | grep -Ei 'block count|reserved block count|block size'

# drop it to 1% (or -m 0 for none). Works while mounted.
sudo tune2fs -m 1 /dev/sdb1

# or set an absolute number of blocks
sudo tune2fs -r 262144 /dev/sdb1   # 1 GiB at 4 KiB blocks

Inode tables: only at format time. Fewer inodes means less overhead. But you can't add inodes later, and running out gives "No space left on device" while df -h still shows free space.

# one inode per 1 MiB, 1% reserve, for a volume of big files
sudo mkfs.ext4 -T largefile4 -m 1 /dev/sdb1

# or pick an explicit ratio
sudo mkfs.ext4 -i 65536 /dev/sdb1

Journal and the rest: leave them alone. You can shrink or drop the journal (tune2fs -O ^has_journal), but it saves 1 GiB out of a terabyte and costs you crash consistency.

Units: nothing to fix. If you'd like df to count the way the box does, use df -H (powers of 1000) instead of df -h (powers of 1024).

Check it on your own system

# raw partition size in bytes
lsblk -b -o NAME,SIZE /dev/sdb1

# what mkfs decided
sudo dumpe2fs -h /dev/sdb1 2>/dev/null | grep -Ei \
  'block count|reserved block count|inode count|inode size|blocks per group|journal size|overhead'

# the kernel's view, in exact bytes
df -B1 /mnt/data
df -i  /mnt/data

Partition bytes minus df Size gives you the metadata. Size − Used − Avail gives you the reserve. The difference between the label and partition bytes is the GPT and alignment. And the leftover gap between what the box says and what df -h says is just GB versus GiB.

Assumptions behind the numbers. Default mke2fs.conf for ext4 on a recent e2fsprogs: 4 KiB blocks, 256-byte inodes, 32,768 blocks per group, and the 64bit, flex_bg, sparse_super and resize_inode features. The partition is GPT, starting at 1 MiB. The kernel reports df in its default bsddf mode, which subtracts metadata from Size (the minixdf mount option reports the raw block count instead). The journal size follows e2fsprogs' default size table. Sizes for an inode-count-limited or bigalloc filesystem, or for non-default mke2fs.conf profiles that some distributions ship, will differ. The "1 TB" example uses 1,000,204,886,016 bytes, a common real capacity for drives sold as 1 TB.
