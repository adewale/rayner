Why int4 and int8 rows can take the same space

You switched a column from bigint to integer to save four bytes per row. The table came out exactly the same size. The four bytes didn't disappear: they turned into padding.

Short answer. On 64-bit builds, PostgreSQL starts every row on an 8-byte boundary and rounds every row's footprint up to a multiple of 8 bytes. The row header is 23 bytes, which rounds up to 24. A row of header + int4 is 28 bytes, so it rounds up to 32. A row of header + int8 is exactly 32. Both rows use 32 bytes on the page, plus a 4-byte pointer, so both tables fit 226 rows per 8 KB page.

1. What a heap page looks like

A table file is a sequence of 8,192-byte pages. Each page has a small header, then an array of 4-byte line pointers growing forward from the start, and the rows themselves (tuples) packed backward from the end. Whatever is left in the middle is free space. When the two regions meet, the page is full.

Two rounding rules matter for the column-width question:

  1. Each column is aligned to its type's boundary. int2 aligns to 2 bytes, int4 to 4, and int8, float8 and timestamptz to 8. If the previous column ends at an awkward offset, padding bytes are inserted first.
  2. Each whole tuple is rounded up to 8 bytes. The next tuple must start on an 8-byte boundary, so the tail of every tuple is padded out.

2. The two rows, byte by byte

Each grid row below is 8 bytes, the alignment unit. The 23-byte tuple header holds the visibility information (xmin, xmax, command id, ctid, flag bits, header length). The data must start at t_hoff, which is itself rounded up to a multiple of 8, so user data always begins at byte 24.

The arithmetic for both tables comes out the same:

usable bytes per page   8192 − 24          = 8168
bytes per row           32 (tuple) + 4 (line pointer) = 36
rows per page           floor(8168 / 36)  = 226

4. When narrowing a column does save space

Shrinking a column only helps if the row ends up crossing one fewer 8-byte boundary. What matters is total length after alignment, not any single column's width. Some cases (all with no NULLs):

The patterns:

  • int4s save space in pairs. Two int4 columns fill one 8-byte word. A single one leaves four bytes of padding beside it.
  • Column order matters. An int4 placed directly before an int8 forces 4 bytes of padding so the int8 can start on an 8-byte boundary. Putting 8-byte-aligned columns first, then 4-, 2- and 1-byte ones, removes that internal padding. The tail rounding still applies.
  • NULLs are free, mostly. A NULL value takes no data bytes, but a row with any NULL gets a null bitmap of one bit per column, stored right after the 23-byte header. With up to 8 columns, the bitmap fits in byte 23, which was padding anyway. With 9 or more columns it pushes the data start from 24 to 32.

5. Indexes round the same way

A B-tree index entry has an 8-byte header (a heap pointer plus flags) followed by the key, and it is also padded to 8 bytes. 8 + 4 = 12 rounds to 16, and 8 + 8 = 16 stays 16. So an index on unique int4 values is generally the same size as one on int8. (B-tree deduplication in PostgreSQL 13+ can change this when values repeat.)

6. Check it on your own server

CREATE TABLE t4 (id int4);
CREATE TABLE t8 (id int8);
INSERT INTO t4 SELECT g FROM generate_series(1, 100000) g;
INSERT INTO t8 SELECT g FROM generate_series(1, 100000) g;

SELECT pg_relation_size('t4') AS t4, pg_relation_size('t8') AS t8;
-- both: 3629056 bytes = 443 pages (100000 / 226, rounded up)

With the pageinspect extension you can see the padding directly:

CREATE EXTENSION pageinspect;
SELECT lp, lp_off, lp_len FROM heap_page_items(get_raw_page('t4', 0)) LIMIT 3;
--  lp | lp_off | lp_len
--   1 |   8160 |     28     ← tuple is 28 bytes long…
--   2 |   8128 |     28     ← …but the next one starts 32 bytes earlier
--   3 |   8096 |     28

Run the same query on t8: lp_len is 32 and the offsets are identical.

What this means when designing a table

  • Don't pick int4 over int8 to save space without doing the arithmetic for the whole row. For many narrow tables, especially a single key column or a key plus timestamps, the saving is zero. Meanwhile a key that outgrows 2,147,483,647 forces a painful migration later.
  • For wide tables with many fixed-width columns, ordering them from widest alignment to narrowest (8 → 4 → 2 → 1, variable-width last) is the reliable way to reclaim padding.
  • Per-row overhead (24-byte header + 4-byte line pointer + tail padding) is often larger than the data itself. For tiny rows, the row count dominates storage, not the column widths.
