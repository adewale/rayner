1. **Bloom filter.** A Bloom filter says "maybe" because a set bit doesn't record which item set it. Adding an item hashes it with k hash functions and sets those k bits in a bit array. A lookup checks the same k bits. If any of them is 0, the item was never added, because adding it would have set that bit. That is why there are no false negatives. If all k bits are 1, they could have been set by other items that happen to share those positions, so all the filter can say is "maybe." The false-positive rate is roughly (1 − e^(−kn/m))^k for n items in m bits. With about 10 bits per item and 7 hashes it comes to about 1%.

2. **Token bucket.** The bucket holds up to B tokens and refills at a steady rate r, for example 10 tokens per second. Each request spends one token. When the bucket is empty, the server answers 429. After a quiet spell the bucket is full, so a burst of up to B requests goes straight through. After that, requests are limited to the refill rate r. A sustained flood drains the bucket and then gets only r per second, with the rest refused. Over any window of t seconds, at most B + r·t requests get through. That one formula is what allows a short burst while still bounding what follows it.

3. **poppy.json.** I don't know a "poppy.json" or Personal Agent spec, so this is a guess at how such a scheme usually works, and my confidence is low. Trust usually comes from where the file is served, not from what it says. The agent fetches it over HTTPS from a fixed path on the shop's own domain, such as `/.well-known/`. The TLS certificate proves the file came from whoever controls that domain. To be stronger, the file can be signed with a key published elsewhere under the domain (DNS or a JWKS endpoint) or vouched for by a registry, so a copy hosted anywhere else counts for nothing. Check chapter 2 of the spec for the actual mechanism.

4. **Birthday paradox.** 23 people are enough for a better-than-even chance (about 50.7%). With 23 people there are 23×22/2 = 253 pairs, and each pair matches with a chance of 1 in 365. The chance that nobody matches is (364/365)×(363/365)×… over 22 factors, about 0.493. With 50 people the chance of a shared birthday is about 97%, and with 70 it is about 99.9%. A crowd of a hundred is far more than you need.

5. **externalTrafficPolicy.** With `Cluster` (the default), the cloud load balancer sends traffic to every node. Each node's kube-proxy then spreads requests across all the Service's pods, even pods on other nodes. That gives an even spread per pod, but it costs an extra hop and replaces the client's source IP with the node's address (SNAT). With `Local`, a node sends traffic only to pods running on that node. Nodes without a pod fail the health check and get no traffic, and the client IP is kept. The catch is that the load balancer usually splits traffic evenly per node, not per pod. So a node with one pod gives that pod as much traffic as a node with three pods shares among all three, and the load becomes uneven.

6. **Periodic table shape.** The shape comes from how many electrons each subshell holds and the order the subshells fill in. s holds 2, p holds 6, d holds 10 and f holds 14. Every row starts by filling an s subshell, which gives the two left-hand columns. Row 1 has only 1s, so it holds just H and He, and that is the gap at the top. Rows 2–3 add a p subshell, giving 2 + 6 = 8 elements. From row 4, a d subshell fills in between, adding 10 middle columns, so those rows hold 18. From row 6, an f subshell adds 14 more, so those rows hold 32. That would make the table too wide, so the lanthanides and actinides are printed as the two rows set apart below. The filling order (1s, 2s, 2p, 3s, 3p, 4s, 3d, 4p, …) follows energy, which is why 3d comes after 4s and each block lands where it does.
