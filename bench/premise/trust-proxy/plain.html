Which address should Express call the client?

Your app sits behind a CDN and a load balancer. Every request it gets arrives from the load balancer, so the real visitor's address has to be read from a header. The trust proxy setting tells Express how far into that header to read. Set it too low and every visitor shares one address. Set it too high and visitors can choose their own.

Short answer. Express should use the address of the first machine you don't run, counting back from your app. That's the address your outermost trusted proxy (the CDN edge) saw connect to it. In practice that means one of two settings:
  • app.set('trust proxy', 2), which trusts two hops: the load balancer and the CDN. This is right if nobody can reach your load balancer without going through the CDN.
  • A list of addresses you control, e.g. app.set('trust proxy', ['loopback', 'uniquelocal', '<your CDN's IP ranges>']). This is sturdier because it checks who each hop is rather than counting hops.
Don't use true in this setup. It lets any visitor pick their own req.ip.

1. What arrives at your app

A TCP connection only tells you about the machine at the other end of it, and for your app that machine is always the load balancer. So each proxy adds a line to the X-Forwarded-For header (XFF): "I received this request from this address." Each proxy adds to the end of whatever header it was given. It doesn't check or replace what's already there.

The key point: each entry is only as trustworthy as the machine that wrote it. Your load balancer wrote the last entry, and you trust your load balancer. The browser can put anything it likes in the header before the CDN ever sees it, and the CDN will pass that text along, adding the real address after it.

2. How Express reads it

Express hands this job to a small library called proxy-addr. It works in three steps:

  1. Make a list, nearest first. Start with the socket address (index 0), then add the XFF entries from right to left. For the example above that gives [10.0.0.5, 198.51.100.20, 203.0.113.7].
  2. Move along the list while each address is trusted. For each address, ask your trust proxy setting: "is this one of my proxies?" (The question is passed the address and its index.)
  3. Stop at the first address that isn't trusted. That address becomes req.ip. If every address is trusted, Express uses the last one in the list, which is the leftmost XFF entry.

So the setting isn't really "how many proxies do I have". It answers "which machines am I willing to believe when they report who connected to them?" req.ip is the first machine you aren't willing to believe. Its address is reliable, because a trusted proxy recorded it, but anything it wrote in the header is not.

req.ips holds the addresses that were examined, in the opposite order: from the client end through to your outermost trusted proxy, leaving out the socket address. It is empty when trust proxy is off.

5. Choosing and checking

Counting hops vs. listing addresses

A number like 2 means "the last two writers are mine, no matter who they are." That only holds if every request takes exactly that path. A list means "trust a hop only if its address is in my ranges." The list keeps working if an attacker reaches the load balancer directly, and it keeps working if the CDN sometimes adds an extra internal hop (some CDNs route through a second "shield" or "origin" tier). The downside is that you have to keep your copy of the CDN's published IP ranges current.

// Count: fine when the LB only accepts traffic from the CDN
app.set('trust proxy', 2);

// List: checks who each hop actually is
app.set('trust proxy', [
  'loopback', 'uniquelocal',      // 127.0.0.0/8, 10/8, 172.16/12, 192.168/16, fc00::/7 ...
  '198.51.100.0/24',              // your CDN's published ranges go here
]);

// Function: full control; i is the index (0 = socket peer)
app.set('trust proxy', (addr, i) => i === 0 || cdnRanges.has(addr));

Set it with app.set before any middleware that reads req.ip, such as a rate limiter or logger, handles requests. Express evaluates the setting on every request, so a later change does take effect, but it's easy to get confused if you change it after startup.

Close the side door

Whatever setting you choose, make the load balancer accept connections only from the CDN, using security groups or firewall rules, or by checking a secret header the CDN adds. If the origin can be reached directly, a count-based setting will believe whatever the attacker writes.

Check it in production

app.get('/_whoami', (req, res) => res.json({
  ip: req.ip,
  ips: req.ips,
  xff: req.get('x-forwarded-for'),
  socket: req.socket.remoteAddress,
}));

Request it normally, then again with curl -H 'X-Forwarded-For: 1.2.3.4'. ip should show your real public address both times. If the second request shows 1.2.3.4, you're trusting too much. If ip is one of your proxies' addresses, you're trusting too little. Remove the route once you're done.

The same setting controls other headers

trust proxy also decides whether Express believes X-Forwarded-Proto for req.protocol and req.secure (which matter for secure cookies and HTTPS redirects), and X-Forwarded-Host for req.hostname. For those headers Express only asks whether the socket peer is trusted. If you widen the setting to fix req.ip, you're trusting those headers too.

Things that can trip you up

  • Some CDNs put the client in a separate header as well (for example a "connecting IP" or "true client IP" header). Express ignores those. It only reads XFF, so the CDN still has to append to XFF, and most do.
  • Multiple X-Forwarded-For headers are joined by Node into one comma-separated list, so splitting the value across headers doesn't get around anything.
  • If IPv4 addresses show up as ::ffff:10.0.0.5, that's the same address written in IPv6 notation. proxy-addr matches it against IPv4 ranges correctly.
  • The newer standard Forwarded header is not read by Express.
