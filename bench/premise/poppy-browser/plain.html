How the agent's browser joins the Session without ever carrying the key

The agent already has a Session with the shop: it signs every API call with the seal (the Session header: who is asking) and the key (the access token: what the account allows). Now it has to drive a real browser through the shop's website, because some things (a checkout page, a 3-D Secure prompt, a size picker) only exist as web pages. The browser needs to be inside the same Session. It must not get the key.

The short answer. The agent stays on its own server and uses the key once, over the back channel, to ask the shop for a join code: a one-time, 30-second ticket bound to its Session and to one specific browser. The browser hands the code to the shop and gets back an ordinary first-party session cookie that points at the same Session record. From then on the cookie does the job of the seal for that browser. The shop looks up the account's permissions on its own side; the browser never holds anything it could use against the API.

If you know OAuth, this is the authorization-code flow with PKCE turned around. In OAuth the browser carries a code to the back end, which swaps it for a token. Here the back end, which already has the token, mints a code that the browser swaps for a cookie.

1. Why not just give the browser the key?

Because the browser is the most exposed place the agent works in. It runs scripts written by the shop, the shop's analytics vendors and its ad partners. Pages can contain text written to steer the agent (prompt injection). The agent takes screenshots and keeps logs of what it saw. An access token is a bearer credential: whoever holds it can use it from anywhere, against every API the account allows, until it expires. Putting it in localStorage or a URL means any of those parties can walk off with the whole account.

There is also a plainer reason: a browser can't attach the seal anyway. When you click a link or submit a form, the browser makes the request. It sends cookies, but you can't add an Authorization or Session header to a top-level navigation. So the web side of the shop needs the Session in a form a browser carries by itself, and that form is a cookie.

Two doors, one Session. What the agent may do through either door comes from the Session record, which the shop keeps. The cookie only says which record to use.

3. What each piece is for

  • join=J: a random value in an HttpOnly, Secure, SameSite=Strict cookie. Page scripts can't read it and other sites can't make the browser send it. It ties the handoff to this browser, the way the PKCE verifier ties an OAuth code to one client.
  • C = hash(J): the public half. It can appear in the page and in the agent's logs, because nobody can work J out from it.
  • H: the join code. The shop only mints one for a caller that shows the key and seal, so minting it is the step where the account says "this browser may act for me." It's single-use, lives for 30 seconds and works only alongside J.
  • sid: the result, an ordinary session cookie (__Host- prefix, HttpOnly, Secure, SameSite=Lax). On the shop's side it points at Session S. It carries no permissions itself: no scopes, no token, nothing the API would accept.

Why does the agent type the code into a form on the shop's own page instead of loading /join?code=H? URLs end up in history, Referer headers, proxy logs and screenshots. A same-site POST keeps H out of all of those, and since J is SameSite=Strict, the POST only works when it comes from the shop's own page.

5. The cross-site form post that has to fail

You know cross-site request forgery: a hostile page auto-submits a form to another site, and the browser attaches that site's cookies. Two versions of it matter here.

Forcing a purchase. evil.example posts a hidden form to shop/checkout/confirm while the agent's browser is joined. Because sid is SameSite=Lax, the browser leaves it off cross-site POSTs, so the shop sees a request with no Session and turns it down. Normal CSRF tokens on the shop's forms back this up.

Joining the wrong Session. The nastier one: the attacker mints a join code in their own Session and gets the agent's browser to submit it. If that worked, the agent would be shopping inside the attacker's account, typing in your address and card. (This is "login CSRF", or session swapping.) It fails because the shop also wants a J whose hash is the C that was sent with that code. The attacker's code is bound to the attacker's C, and the cross-site post doesn't carry the browser's J anyway.

6. One Session, one off switch

Because the cookie points at the Session and doesn't copy anything out of it, everything that governs the Session governs the browser too:

  • Same audit trail. API calls made with the seal and clicks made with the cookie are logged under Session S, so the account owner sees one story, not an API story and a mystery browser.
  • Same limits, or tighter. The shop can give the web side less than the key allows, for example browse and pay up to the Session's spending cap but never change the password. It can't give more, because the browser's authority is read from the Session.
  • Same end. When the agent ends Session S, or the user revokes it, or the key's grant is withdrawn, the shop drops every sid that points at S. Nobody has to hunt down a browser.

In one line: the key stays on the agent's server and is used once, to ask for a short-lived ticket bound to one browser. The browser swaps the ticket for a cookie. The cookie stands in for the seal and points at the same Session, so the browser works inside it without ever holding what the account allows.
